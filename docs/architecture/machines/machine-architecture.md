# Концептуальная архитектура машин

**Статус:** утверждённые принципы + явно обозначенные варианты для будущего дизайна.  
**Источник:** [реестр AS-MACHINE-001–020](README.md#реестр-решений).

## Для чего нужна архитектура

Общие правила должны одинаково работать для генератора угля, электрической печи, хранилища энергии, химического реактора и мультиблочной фабрики. Не стоит разрабатывать иерархию «абстрактный генератор → абстрактная машина → абстрактный сложный генератор» до появления доказанных общих обязанностей.

## Концептуальные составляющие (не названия готовых Java-классов)

```text
Механизм (BlockEntity или контроллер мультиблока)
│
├── Политика поддерживаемых функций и портов
├── Конфигурация разрешённых граней/маршрутов
├── Внутренние ресурсные хранилища
│   ├── Энергетический буфер
│   ├── Предметные группы слотов
│   ├── Жидкостные резервуары
│   └── Газовые резервуары
├── Обработчики внешних capabilities и маршрутизация
├── Планировщики автоматического ввода/вывода (опционально)
├── Политика выбора рецепта (опционально)
├── Рабочие камеры и операции (опционально)
├── Координатор атомарных операций (при производстве)
└── Сохранение состояния / уведомления / проекции для GUI
```

Это **разделение ответственности**, а не требование по одному классу на каждую строку.

## Главные границы

| Понятие | Не равно |
|---|---|
| Физическая грань | Логический канал |
| `MachineSide` (`FRONT`, `BACK`, `LEFT`, `RIGHT`, `TOP`, `BOTTOM`) | Мировой `Direction` |
| Идентификатор порта | Направление `Direction` |
| `INPUT`/`OUTPUT` как маршрут | Роль внутреннего резервуара |
| `SERVICE` как маршрут | Обычный производственный `OUTPUT` |
| Пассивное разрешение доступа | Активное действие АвтоВход/АвтоВыход |
| Выбранный рецепт | Уже запущенная операция |
| Логическое резервирование | Списание ингредиентов |
| Место в выходном буфере | Уже подтверждённая выдача набора продуктов |

## Идентичность портов

Для энергии **уже реализован** `EnergyPortId`: устойчивая логическая идентичность **в пределах одного механизма**, не глобальный адрес мира, независимо от ориентации `Direction`. Менеджер использует его для спроса, передачи и справедливости. Это важно для будущего мультиблока с двумя портами, обращёнными в одну сторону; физическая интеграция таких хэтчей ещё впереди. Возможные эквиваленты для других типов ресурсов — **не утверждённые имена API**; сначала определить, нужен ли отдельный стабильный `portId` для каждой категории и как маршруты проецируются на NeoForge side capability.

## Пример физической компоновки

На задней грани электрической печи теоретически могут сосуществовать предметный вход и энергетический вход, если конструкция это позволяет. Но внешний кабель и внешняя труба должны уметь физически разместиться/стыковаться. Возможность одновременного подключения в *одном соседнем блоке* не является частью этих ADR.

## Мультиблоки

Контроллер владеет общим состоянием. Физические хэтчи/порты обращаются к соответствующему внутреннему хранилищу/политике контроллера. Не создаём независимый энергетический буфер на каждом фасадном порту, если это не отдельное игровое требование.

**Планируемая физическая компоновка:** мультиблок строится из **отдельных специализированных блоков-портов**. Для разных видов ресурсов и направлений предполагаются самостоятельные блоки, например: энергетический вход, энергетический выход, предметный вход, предметный выход, жидкостный вход и жидкостный выход. Один хэтч не обязан совмещать несколько видов ресурсов или одновременно служить входом и выходом.

Это **уточнение области применения** архитектуры нескольких каналов на одной грани: [AS-MACHINE-001](decisions/AS-MACHINE-001.md) и [AS-MACHINE-021](decisions/AS-MACHINE-021.md) остаются актуальны для обычных одноблочных машин, если их конструкция допускает несколько каналов. Для специализированных хэтчей мультиблоков такое совмещение **не требуется**.

Несколько отдельных энергетических хэтчей могут иметь одинаковый мировой `Direction`; у них всё равно должны быть **разные `EnergyPortId`** внутри контроллера. Геометрия хэтчей, виды блоков, конкретные маршруты `SERVICE` и API связи с контроллером будут определены позднее; сейчас это не готовая реализация.

## Анти-паттерны

- Отдельные почти идентичные классы `CoalGeneratorPort`, `LavaGeneratorPort` и т. п. только ради смены владельца.
- Большой монолитный `ResourceComponent<T>` для FE, предметов, жидкости, газа без учёта их специфики.
- Прямое изменение внутренних слотов из GUI/пакета в обход серверных политик.
- Два источника истины для одного порта: NBT-конфигурация плюс независимо меняемый BlockState.
- Хранение `Direction` вместо идентификатора порта в справедливом распределителе.
- Избыточное создание базовых классов прежде, чем подтверждена общая функциональность.

## Граница текущего этапа

Базовые FE-классы (`EnergyComponent`, `EnergyPortId`, режимы, политики, `EnergyDistributionManager`) и их собственные методы **уже существуют**. При этом универсальные **контракты их совместной координации**, `EnergyPortHandler`, схемы интеграции GUI/сохранения и полный протокол газовой интеграции **ещё не определены**. Существующий `EnergyComponent` реализует хранение FE и транзакционные операции, но пока не координирует порты/бюджеты. См. [энергетическую систему](energy-system.md) и [открытые вопросы](open-questions.md).


## Дополнение 2026-11-05: визуальное состояние и физические коммуникации

[Локальный эксперимент](visual-model-prototype.md) подтвердил возможность обновлять состав запечённых частей модели через `ModelData` и `DynamicBlockStateModel` без дополнительных флагов конфигурации в `BlockState` (кроме ориентации `FACING`). Это **не** завершённая миграция Coal Generator Mk I и **не** утверждённый универсальный Java API.

Для одноблочных механизмов разделяем:

- Серверный логический ресурсный порт: правила доступа, устойчивая идентичность и внутренние маршруты.
- Машинную визуальную область: расположение, панель/заглушка/модуль, embedded или overlay.
- Физическую точку стыковки: позицию мини-разъёма на грани.
- Канал собственного составного транспорта в соседнем блоке: отдельную сеть, лимиты и форму.

Одна грань может иметь несколько областей/портов. Для **собственных** труб и проводов целевой [составной транспорт](conduit-system.md) допускает несколько каналов в одной клетке; появление геометрической обёртки у машины автоматическое. Для сторонних модов сохраняем стандартные capabilities по типу ресурса и направлению; специально совместно размещать собственный блок с кабельным блоком AE2 не требуется.

Для мультиблоков сохранены физически отдельные специализированные хэтчи с общим контроллером. Шаблонов сечения 1–5 транспортного блока **не переносить** на ограничение числа портов машины.
