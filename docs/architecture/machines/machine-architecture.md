# Концептуальная архитектура машин

**Статус:** утверждённые принципы, целевая FE-архитектура генераторов и отдельно помеченные будущие возможности.  
**Актуализировано:** 2026-11-24.  
**Источник:** [реестр ADR](README.md#реестр-решений), [AS-MACHINE-023](decisions/AS-MACHINE-023.md), [AS-MACHINE-024](decisions/AS-MACHINE-024.md), [AS-MACHINE-025](decisions/AS-MACHINE-025.md), [AS-MACHINE-026](decisions/AS-MACHINE-026.md), [AS-MACHINE-027](decisions/AS-MACHINE-027.md).

## Для чего нужна архитектура

Общие правила должны одинаково работать для генератора угля, электрической печи, хранилища энергии, химического реактора и мультиблочной фабрики. Для энергетических механизмов и генераторов общие обязанности уже подтверждены; выбранная узкая иерархия и композиция зафиксированы в AS-MACHINE-023. Продолжать углублять наследование без доказанной потребности не следует.

## Концептуальные составляющие (не названия готовых Java-классов)

```text
Механизм (BlockEntity или контроллер мультиблока)
│
├── Политика поддерживаемых функций и портов
├── Конфигурация разрешённых граней/маршрутов
├── Внутренние ресурсные хранилища
│   ├── Энергетический буфер
│   ├── Предметные группы слотов
│   ├── Жидкостные резервуары
│   └── Газовые резервуары
├── Обработчики внешних capabilities и маршрутизация
├── Планировщики автоматического ввода/вывода (опционально)
├── Политика выбора рецепта (опционально)
├── Рабочие камеры и операции (опционально)
├── Координатор атомарных операций (при производстве)
└── Сохранение состояния / уведомления / проекции для GUI
```

Это **разделение ответственности**, а не требование по одному классу на каждую строку.

## Главные границы

| Понятие | Не равно |
|---|---|
| Физическая грань | Логический канал |
| `MachineSide` (`FRONT`, `BACK`, `LEFT`, `RIGHT`, `TOP`, `BOTTOM`) | Мировой `Direction` |
| Идентификатор порта | Направление `Direction` |
| `INPUT`/`OUTPUT` как маршрут | Роль внутреннего резервуара |
| `SERVICE` как маршрут | Обычный производственный `OUTPUT` |
| Пассивное разрешение доступа | Активное действие АвтоВход/АвтоВыход |
| Выбранный рецепт | Уже запущенная операция |
| Логическое резервирование | Списание ингредиентов |
| Место в выходном буфере | Уже подтверждённая выдача набора продуктов |

## Идентичность портов

Для энергии **уже реализован** `EnergyPortId`: устойчивая логическая идентичность **в пределах одного механизма**, не глобальный адрес мира, независимо от ориентации `Direction`. Менеджер использует его для спроса, передачи и справедливости. Это важно для будущего мультиблока с двумя портами, обращёнными в одну сторону; физическая интеграция таких хэтчей ещё впереди. Возможные эквиваленты для других типов ресурсов — **не утверждённые имена API**; сначала определить, нужен ли отдельный стабильный `portId` для каждой категории и как маршруты проецируются на NeoForge side capability.

## Пример физической компоновки

На задней грани электрической печи могут сосуществовать независимые предметный вход и энергетический вход, если конструкция это разрешает. Для **собственного** транспорта Astral Space согласовано совместное размещение независимых проводов и труб в **одном соседнем составном блоке** с автоматической стыковкой ([AS-MACHINE-022](decisions/AS-MACHINE-022.md)); конкретные геометрические формы и реализация остаются отдельными задачами. Сторонние моды получают стандартные capabilities по стороне и не обязаны разделять эту клетку.

## Мультиблоки

Контроллер владеет общим состоянием. Физические хэтчи/порты обращаются к соответствующему внутреннему хранилищу/политике контроллера. Не создаём независимый энергетический буфер на каждом фасадном порту, если это не отдельное игровое требование.

**Планируемая физическая компоновка:** мультиблок строится из **отдельных специализированных блоков-портов**. Для разных видов ресурсов и направлений предполагаются самостоятельные блоки, например: энергетический вход, энергетический выход, предметный вход, предметный выход, жидкостный вход и жидкостный выход. Один хэтч не обязан совмещать несколько видов ресурсов или одновременно служить входом и выходом.

Это **уточнение области применения** архитектуры нескольких каналов на одной грани: [AS-MACHINE-001](decisions/AS-MACHINE-001.md) и [AS-MACHINE-021](decisions/AS-MACHINE-021.md) остаются актуальны для обычных одноблочных машин, если их конструкция допускает несколько каналов. Для специализированных хэтчей мультиблоков такое совмещение **не требуется**.

Несколько отдельных энергетических хэтчей могут иметь одинаковый мировой `Direction`; у них всё равно должны быть **разные `EnergyPortId`** внутри контроллера. Согласованы также `assemblyId`, состояния `UNFORMED` / `FORMED` / `SUSPENDED`, fail-closed при неполной загрузке и инвалидация возможностей по позициям физических хэтчей. Подробнее — [AS-MACHINE-026](decisions/AS-MACHINE-026.md). Геометрия хэтчей, конкретные маршруты `SERVICE` и Java API связи с контроллером будут определены позднее; сейчас это не готовая реализация.

## Анти-паттерны

- Отдельные почти идентичные классы `CoalGeneratorPort`, `LavaGeneratorPort` и т. п. только ради смены владельца.
- Большой монолитный `ResourceComponent<T>` для FE, предметов, жидкости, газа без учёта их специфики.
- Прямое изменение внутренних слотов из GUI/пакета в обход серверных политик.
- Два источника истины для одного порта: NBT-конфигурация плюс независимо меняемый BlockState.
- Хранение `Direction` вместо идентификатора порта в справедливом распределителе.
- Избыточное создание базовых классов прежде, чем подтверждена общая функциональность.

## Принятая FE-иерархия и композиция (2026-11-24)

```text
BlockEntity
└── AbstractEnergyMachineBlockEntity (один EnergyComponent)
    ├── AbstractGeneratorBlockEntity (FE OUTPUT, генерация)
    │   ├── CoalGeneratorBlockEntity
    │   └── LavaGeneratorBlockEntity
    ├── AbstractEnergyConsumerBlockEntity (FE INPUT, расход на работу)
    │   ├── ElectricCompressorBlockEntity
    │   ├── ElectricCrusherBlockEntity
    │   └── ElectricFurnaceBlockEntity
    └── EnergyStorageBlockEntity (FE INPUT + OUTPUT, общий буфер)
```

Это **целевая иерархия**, не реализованная полностью в `main`. Обязательная энергетическая база не знает о топливе, Fluid, Push, рецептах и портах; генераторный слой подключает отдельный `EnergyOutputController`. Независимый `EnergyInputController` предназначен для входящих контуров потребителей/накопителей. Для совместимости с текущим `EnergyPortHandler` используется тонкий `EnergyPortDispatcher` — без дублирования алгоритмов. `AbstractMachineBlockEntity` и `AbstractFuelCycleGeneratorBlockEntity` не вводим.

**Потребитель (Consumer)** использует входящие FE-порты с общим входным бюджетом и внутренний расход FE для полностью оплаченного рабочего тика, **не** выходной распределитель. **Накопитель (Energy Storage)** использует входной и выходной контроллеры **над одним EnergyComponent**, с независимыми бюджетами направления, не производит FE и сам инициирует Push через разрешённые OUTPUT-порты и не наследуется от генератора ради этой функции. **`AbstractEnergyConsumerBlockEntity` входит в утверждённую иерархию**; для накопителя определено прямое наследование от общей FE-базы, а отдельный `AbstractEnergyStorageBlockEntity` пока не нужен. Точные конструкторы Consumer и Input-контроллера ещё не согласованы; см. [AS-MACHINE-027](decisions/AS-MACHINE-027.md).

Производственный алгоритм, состояние топлива и конкретная физическая топология разделены: см. [общую FE-базу](decisions/AS-MACHINE-023.md), [конфигурацию и топологию](decisions/AS-MACHINE-024.md) и [Strategy/топливный цикл](decisions/AS-MACHINE-025.md).

## Граница текущего этапа

`EnergyComponent`, `EnergyPortId`, политики, `EnergyPortHandler`, `EnergyTransferCoordinator`, `EnergyDistributionManager` и другие FE-узлы **реализованы**. Выделение `EnergyInputController`, `EnergyOutputController`, `EnergyPortDispatcher` и общей генераторной иерархии **согласовано, но ещё не реализовано**. `LavaGeneratorBlockEntity` в `main` демонстрирует современную BE-конфигурацию и динамический рендеринг; Coal пока использует старую схему BlockState-флагов. Газовое API остаётся отдельной будущей задачей. См. [энергетическую систему](energy-system.md) и [открытые вопросы](open-questions.md).


## Дополнение 2026-11-05: визуальное состояние и физические коммуникации

[Локальный эксперимент](visual-model-prototype.md) подтвердил возможность обновлять состав запечённых частей модели через `ModelData` и `DynamicBlockStateModel` без дополнительных флагов конфигурации в `BlockState` (кроме ориентации `FACING`). Это **не** завершённая миграция Coal Generator Mk I и **не** утверждённый универсальный Java API.

Для одноблочных механизмов разделяем:

- Серверный логический ресурсный порт: правила доступа, устойчивая идентичность и внутренние маршруты.
- Машинную визуальную область: расположение, панель/заглушка/модуль, embedded или overlay.
- Физическую точку стыковки: позицию мини-разъёма на грани.
- Канал собственного составного транспорта в соседнем блоке: отдельную сеть, лимиты и форму.

Одна грань может иметь несколько областей/портов. Для **собственных** труб и проводов целевой [составной транспорт](conduit-system.md) допускает несколько каналов в одной клетке; появление геометрической обёртки у машины автоматическое. Для сторонних модов сохраняем стандартные capabilities по типу ресурса и направлению; специально совместно размещать собственный блок с кабельным блоком AE2 не требуется.

Для мультиблоков сохранены физически отдельные специализированные хэтчи с общим контроллером. Шаблонов сечения 1–5 транспортного блока **не переносить** на ограничение числа портов машины.

## Инвариант режимов граней (пересмотр 2026-11-08)

Разные типы ресурсов могут сосуществовать на одной грани, но каждый из них имеет лишь один режим: INPUT, OUTPUT, DISABLED; для ITEM/FLUID/GAS при поддержке конструкцией также доступен взаимоисключающий SERVICE. Для FE SERVICE не предусмотрен. Одновременные INPUT + OUTPUT одного типа запрещены. Роли внутренних баков и слотов, а также собственные настройки направления и фильтров труб не изменяют разрешения машины. Жидкостная сеть содержит один текущий тип жидкости и автоматически освобождает его, когда полностью пуста; это не постоянная привязка пустого бака.
