# AS-MACHINE-024 — Конфигурация FE-портов, топология и runtime-доступность

**Статус:** утверждено как целевая архитектура 2026-11-24; уточнено 2026-11-26: номинальная генерация входит в `GeneratorEnergySpec`. Расширение спецификации и интеграция с базовым генератором описываются как целевой контракт.  
**Область:** генераторы и физические подключения FE.  
**Связанные решения:** [001](AS-MACHINE-001.md), [003](AS-MACHINE-003.md), [023](AS-MACHINE-023.md), [026](AS-MACHINE-026.md); [ресурсные подключения](../resource-connections.md).

## Разделение трёх аспектов

Конфигурация генератора описывает **три независимых аспекта**:

```java
// Согласована форма объединяющего record;
// имена вложенных типов и пакетов остаются рабочими.
record GeneratorConfiguration(
    GeneratorEnergySpec energy,
    EnergyPortRules portRules,
    EnergyPortTopology topology
) {}
```

1. **`GeneratorEnergySpec`**: неизменяемые энергетические характеристики генератора — вместимость общего FE-буфера (`long energyCapacity`), суммарная максимальная скорость внешней выдачи (`int maxOutputPerTick`) и номинальное производство за успешный производственный тик (`int generationPerTick`). Расход топлива, длительность топливного цикла и фактическая выработка не входят в спецификацию. Лимит Push/Pull и номинальная генерация остаются независимыми величинами.
2. **`EnergyPortRules`**: декларативные правила логических `EnergyPortId` — исходный режим и множество разрешённых режимов каждого порта, а также неизменяемый признак FIXED/CONFIGURABLE на уровне всего механизма.
3. **`EnergyPortTopology`**: неизменяемое физическое расположение точек подключения и преобразование локальной ориентации в мировую; не хранит пользовательские режимы.

`EnergyPortRule` описывает **один логический порт**, не включает физические координаты. Актуальный изменяемый режим принадлежит `EnergyPortConfiguration` в `BlockEntity`; runtime-доступность проверяется через **живую** `EnergyPortPolicy`. Ни `GeneratorConfiguration`, ни визуальная модель не заменяют эти динамические правила.

### Уточнение GeneratorEnergySpec (2026-11-26)

Согласованный целевой Java-контракт:

```java
public record GeneratorEnergySpec(
    long energyCapacity,
    int maxOutputPerTick,
    int generationPerTick
) {}
```

Отдельный `GeneratorProductionSpec` не вводится: `GeneratorEnergySpec` уже является специализированным описанием энергетических характеристик генератора, а разделение статической конфигурации на два record ради одного поля не даёт необходимой самостоятельной ответственности. `GeneratorConfiguration` сохраняет прежние три компонента. Это изменение структуры конфигурации, а не объединение runtime-обязанностей: `EnergyComponent` хранит FE, выходной контроллер ограничивает выдачу, `AbstractGeneratorBlockEntity` координирует запись полной производственной порции, а `GenerationProcess` подготавливает и завершает производственный тик. Параметры конкретного топлива остаются за пределами `GeneratorEnergySpec`.

## Передача конфигурации при конструировании

Конкретный генератор передаёт единый неизменяемый объект `GeneratorConfiguration` базовому генератору через `super(..., generatorConfiguration)`. Базовый класс собирает FE-инфраструктуру из этого объекта, не запрашивая характеристики через переопределяемые методы наследника. Полная сигнатура конструктора ещё не определена.

## FIXED и CONFIGURABLE

Для начального этапа **все FE-порты одной машины** либо фиксированы, либо настраиваемы. Смешивание фиксированных и настраиваемых портов в одном механизме **отложено**, а не запрещено навсегда.

- `FIXED`: для каждого порта `allowedModes` содержит ровно `defaultMode`; пользователь не переключает режим. Используется `FixedEnergyPortPolicy`; изменяемая `EnergyPortConfiguration` не создаётся. Пользовательские режимы сохраняются только для CONFIGURABLE.
- `CONFIGURABLE`: для каждого порта `allowedModes` содержит не менее двух режимов, включая `defaultMode`. Используется `ConfigurableEnergyPortPolicy` с `EnergyPortConfiguration`.
- Тип настройки всего механизма хранится в неизменяемом `EnergyPortRules` и указывается **явно**, а не выводится из числа разрешённых режимов. Точное имя enum/формат вложенной записи ещё не утверждены.
- У **генератора** разрешены только `OUTPUT` и `DISABLED`; `INPUT` запрещён в описании, при настройке и при восстановлении NBT.
- Идентификаторы, определённые правилами, должны согласовываться с топологией; валидировать уникальность логических ID и физических точек и положительные параметры. Окончательные конструкторы вложенных спецификаций ещё не утверждены.


- `GeneratorEnergySpec` в своём компактном конструкторе проверяет `energyCapacity > 0`, `maxOutputPerTick > 0` и `generationPerTick > 0`, а также соответствие полной производственной порции ёмкости. Нарушение любого из этих инвариантов приводит к `IllegalArgumentException`. `GeneratorConfiguration` сохраняет проверки согласованности наборов `EnergyPortId` и генераторных режимов; вложенные типы отвечают за собственные инварианты и защитное копирование коллекций. Сам по себе `record` **не гарантирует глубокой неизменяемости**.
- Для `FULL-TICK-OR-PAUSE` `GeneratorEnergySpec` обеспечивает **`0 < generationPerTick <= energyCapacity`** при создании, а не каждый серверный тик. Соотношение `generationPerTick` и `maxOutputPerTick` не ограничивается: номинальная генерация может быть больше, меньше или равна лимиту выдачи. Исходящий лимит также не обязан быть меньше или равен ёмкости. Фактическая передача по-прежнему ограничена доступным запасом, бюджетом и политикой портов.

**Независимые оси:** фиксированная *геометрия* порта не означает фиксированный *режим*.

**Границы первой версии:** положение физических FE-точек задаётся **неизменяемым определением**, не пользовательским редактором динамически переставляемых портов; изменение `FACING` или runtime-доступности **не меняет** `EnergyPortId` и пользовательский режим. Горизонтальные повороты — **только** `NORTH/EAST/SOUTH/WEST`; свободное 3D-вращение, зеркальное отражение и изменение вертикальной оси не входят в первый контракт. Заложенная математическая схема не запрещает будущие расширения, но их семантика и Java API пока не утверждены.

## Сборка политики портов (уточнение 2026-11-26)

Для устранения дублирования сборки FIXED/CONFIGURABLE между генераторами, потребителями и накопителями используется общая `EnergyPortPolicyFactory` в `common.energy.port`. Это stateless `public final` utility-класс с приватным конструктором и статическим методом; отдельный интерфейс фабрики и кэширование не вводятся.

Согласованный контракт (сигнатуры без реализации):

```java
public record Result(
    @NonNull EnergyPortPolicy policy,
    @Nullable EnergyPortConfiguration configuration
) {}

public static @NonNull Result create(
    @NonNull EnergyPortRules rules,
    @NonNull Predicate<EnergyPortId> availability,
    @NonNull Consumer<EnergyPortId> onConfigurationChanged
);
```

`Result` — вложенный record фабрики. Его компактный конструктор отклоняет `null` для `policy`; согласованность возвращаемой пары гарантирует именно фабричный метод, а не произвольное прямое создание `Result`. Все три аргумента `create` обязательны (`NullPointerException` при `null`), даже если callback не используется в FIXED.

- FIXED: создаётся `FixedEnergyPortPolicy` из `rules.defaultModes()` и переданного предиката; `configuration == null`.
- CONFIGURABLE: создаётся `EnergyPortConfiguration` из `rules.defaultModes()` и callback `Consumer<EnergyPortId>`; `ConfigurableEnergyPortPolicy` получает `rules.allowedModes()`, ссылку на `getMode` именно возвращаемой конфигурации и тот же предикат доступности. Callback получает ID фактически изменённого порта ровно один раз после записи режима. При запрещённом/неизменном режиме, чтении и тихом `restoreModes` уведомления нет. FIXED callback не использует, но ненулевость обязательна. Контракт Fluid и топливных callbacks не меняется.
- Каждый вызов создаёт независимые компоненты; допускаются пустые правила обоих типов. Фабрика универсальна по направлению передачи, поэтому не запрещает INPUT сама: ограничения генератора остаются в `GeneratorConfiguration`.
- При сборке не вызываются предикат доступности и callback изменения конфигурации. Фабрика не обращается к миру, не меняет режимы, не выполняет NBT-восстановление или `refreshAvailablePorts()` и не создаёт FE-контроллеры. Живую доступность и побочные эффекты изменения режимов определяет владелец.

Эта фабрика заменяет повторяющийся выбор реализации в конструкторах механизмов, а не меняет контракты существующих политик.

## Топология и поворот

- На первом этапе: один `EnergyPortId` ↔ одна физическая точка подключения. Физические точки одной сборки уникальны; два разных порта могут иметь один мировой `Direction`.
- Топология декларативная, относительно опорной позиции и исходного `FACING=NORTH`, преобразование рассчитывается для `NORTH/EAST/SOUTH/WEST`. Опорная позиция **не обязана** совпадать с контроллером.
- Сохраняется семантика `MachineSide` в существующем проекте: при `FACING=NORTH` `LEFT` соответствует мировому **EAST**, `RIGHT` — **WEST**. Не заменять её интуитивным зеркальным толкованием.
- Идентификатор порта остаётся неизменным при повороте; мировая позиция/сторона — вычисляемая геометрия, а не часть идентичности `EnergyPortId`.
- `EnergyPortTopology` одинаково преобразует локальные точки одноблочной машины и мультиблока относительно origin и FACING; не вводить ветвление `isMultiblock` ради одинаковой математики. Проверка состояния конструкции принадлежит политике и владельцу структуры, а не топологии.
- При действительном изменении ориентации пересчитать мировые точки, согласовать доступность портов вне FE-транзакций, при необходимости инвалидировать затронутые физические capability-позиции. Логические ID и пользовательские режимы сохраняются. Конкретная доставка события поворота ещё открыта.

**Утверждённое математическое преобразование** локального смещения `(x,y,z)` относительно NORTH (`+X=EAST`, `+Y=UP`, `+Z=SOUTH`):

| FACING | Локальное смещение → мировое смещение |
|---|---|
| NORTH | `( x, y,  z)` |
| EAST | `(-z, y,  x)` |
| SOUTH | `(-x, y, -z)` |
| WEST | `( z, y, -x)` |

`worldPos = origin + rotate(localOffset, facing)`. Внешняя грань поворачивается **тем же** поворотом; `UP`/`DOWN` не меняются. `MachineSide` сохраняет существующий контракт: `FRONT → facing`, `BACK → opposite`, `LEFT → clockwise`, `RIGHT → counterclockwise`. Канонический NORTH поэтому даёт LEFT=EAST, RIGHT=WEST.

**Контрольный пример:** `origin=(100,64,200)`, `P1=(-1,0,1)`, `P2=(1,0,1)`, обе наружу SOUTH. При NORTH: `P1=(99,64,201,SOUTH)`, `P2=(101,64,201,SOUTH)`; при EAST: `P1=(99,64,199,WEST)`, `P2=(99,64,201,WEST)`. `EnergyPortId` каждого порта остаётся прежним.

**Согласованы формулы и принципы**, не Java-имя/пакет mapper или конкретный API результата. Проверять все четыре ориентации, вертикальные грани и независимость двух портов с одной мировой стороной.

## Дополнительные инварианты портовой модели

- Один логический `EnergyPortId` соответствует **одной физической точке**, описываемой парой `(localOffset, localOutwardFace)`; пара мировых `(BlockPos, Direction)` после поворота должна быть однозначной. **Разные** `EnergyPortId` могут иметь **один и тот же мировой `Direction`**, если физические точки различны. Для одноблочного генератора **`origin = BlockEntity.getBlockPos()`**, а все локальные смещения FE-точек равны **`(0,0,0)`**, различаются внешние грани. Для мультиблока текущий проектный вариант использует позицию контроллера как `origin`, а хэтчи могут иметь ненулевые смещения. Ни одно из этих правил не требует отдельного `ControllerBlockEntity` у обычного блока.
- Наборы логических ID в `EnergyPortRules` и `EnergyPortTopology` должны быть согласованы; для **первой реализации допустимо требовать точного совпадения множеств**, однако обязательное правило точного равенства для всех будущих конструкций **не утверждено**. `DISABLED` означает запрещённый режим, **не отсутствие** описанной физической точки.
- У `EnergyPortRule` непустой `allowedModes` и `defaultMode ∈ allowedModes`. Для `FIXED` число разрешённых режимов **ровно одно**; для `CONFIGURABLE` — **не менее двух**. У генератора ни один из них не равен `INPUT`. Эти инварианты проверяются при построении неизменяемой конфигурации/энергетической инфраструктуры, **не каждый тик**; runtime-право проверяется отдельно живой политикой.
- Существующие `FixedEnergyPortPolicy` и `ConfigurableEnergyPortPolicy` используют предикат физической доступности (`Predicate<EnergyPortId>`) **без добавления новой обязательной абстракции**. Переиспользуется существующий метод `EnergyPortPolicy.isAvailable(portId)`, а не новый менеджер доступности. Базовый генератор обеспечивает общую готовность серверного мира; конкретная доступность зависит от текущего состояния и физической связи. Предикат, callbacks и `LongSupplier` допустимо создать и сохранить при конструировании, в том числе как отложенные ссылки на владельца. Запрещено выполнять их до готовности необходимых зависимостей и контекста.
- Вложенная `EnergyPortConfiguration` является **единственным** mutable-источником режима CONFIGURABLE; для FIXED отдельный NBT-раздел пользовательских режимов не нужен. При загрузке недопустимые режимы, включая `INPUT`, не должны становиться рабочими и не могут расширить разрешённый список.

## Доступность, режим и геометрический поиск

| Метод политики | Ответственность |
|---|---|
| `getMode(portId)` | Текущий режим логического порта, независимо от runtime-доступности |
| `isAvailable(portId)` | Текущая физическая доступность порта |
| `allowsInsert(portId)` | Доступность и разрешение внешнего приёма FE |
| `allowsExtract(portId)` | Доступность и разрешение внешней выдачи FE |
| `canChangeMode(portId, newMode)` | Допустимость изменения режима |

Фиксированный режим не означает постоянную доступность: при `SUSPENDED` фиксированный `OUTPUT` остаётся `OUTPUT`, но `isAvailable()` возвращает false. Не изменять режим на `DISABLED` для отражения временной недоступности структуры.

При обратном поиске по физическому capability-запросу `EnergyPortTopology.findPort(worldPos, outwardFace, origin, facing)` возвращает логический `EnergyPortId`; `resolvePort(portId, origin, facing)` вычисляет `WorldPortPoint`. Внешняя capability предоставляется через физическую обёртку над стабильным логическим handler. Поворот меняет мировое соответствие, но не ID и не режим. Политика независимо проверяет разрешение передачи.

## Runtime-согласование

- Источник разрешений — `EnergyPortPolicy`. `EnergyOutputController.refreshAvailablePorts()` без аргументов фильтрует известные упорядоченные ID по `allowsExtract` и передаёт список в `EnergyDistributionManager.updateAvailablePorts(...)`.
- Пересчёт вызывается на безопасных границах (**не внутри FE-транзакции**): при серверном `onLoad()`, фактическом изменении режима/физической доступности. Повторный вызов допустим, но исключённые из списка порты теряют историю распределения.
- `EnergyPortHandler` на **каждой операции** повторно спрашивает политику, поэтому даже устаревшая внешняя ссылка не получает FE после отключения; пересчёт — не единственная защита.
- Отдельно от пересчёта обрабатываются последствия runtime-события: `setChanged()`, требуемая инвалидация capabilities, клиентская/визуальная синхронизация. Не выполнять их безусловно из `onLoad()`.
- Не смешивать события энергетических и жидкостных портов. Необязательный защищённый hook генератора может обновить визуальную проекцию FE при runtime-изменении, но **не** вызывается из конструктора и тихого `loadAdditional()`.

**Статус существующего кода:** `LavaGeneratorBlockEntity` в `main` уже хранит настройки в BE и использует `ModelData`/`DynamicBlockStateModel`. Coal использует историческую схему `BlockState.OUTPUT_*`. Последняя не должна определять контракт нового генераторного базового класса.

Правила физических хэтчей и жизненного цикла мультиблока — [AS-MACHINE-026](AS-MACHINE-026.md). Подробности FE-контроллера — [AS-MACHINE-023](AS-MACHINE-023.md).

## Уточнение физической привязки после поворота (аудит 2026-11-24)

При повороте сохраняются логические ID и пользовательские режимы, но меняется физическая привязка. Одной проверки режима недостаточно. Целевой контракт 9.9: `public final class EnergyEndpointHandler implements EnergyHandler` с конструктором `EnergyEndpointHandler(@NonNull EnergyHandler delegate, @NonNull BooleanSupplier validity)`. При актуальной привязке делегирует четыре операции EnergyHandler; при недействительной возвращает 0 (включая запас/ёмкость), не обходя проверку некорректных аргументов. Обёртка не управляет миром, бюджетом или политикой; проверку готовности, идентичности владельца, исходной мировой точки и актуальной записи привязки определяет владелец. По одному логическому handler на ID и не более одной актуальной физической обёртки на ID. Неизменное подключение сохраняет экземпляр, изменение только режима не отзывает физическую обёртку (живая политика блокирует передачу); физическое перемещение, уничтожение точки, выгрузка владельца или замена отзывают её окончательно, в том числе при повороте обратно. Инвалидация NeoForge не заменяет проверку старой ссылки. Инвалидировать изменившиеся физические позиции, включая прежние и новые, после актуализации состояния. Структура кэша, доставка событий и точный API отзыва ещё не реализованы и уточняются в 9.16/интеграции.

## Целевой контракт физической доступности (9.8, 2026-11-26)

- Приватный `boolean isEnergyPortAvailable(EnergyPortId portId)` — предикат для фабрики: проверяет аргумент и runtime-готовность, находит известную точку и делегирует `protected boolean isEnergyPortPhysicallyAvailable(EnergyPortPoint point)`. По умолчанию доступна точка с нулевым local offset при готовности runtime; вынесенная точка требует специальной реализации. Мультиблок переопределяет проверку для всех зависимых от структуры точек, включая нулевые. Не связывать доступность с режимом, наличием кабеля, запасом FE или бюджетом.
- Защищённая проверка — лёгкое чтение уже известного состояния: без мутаций, полного сканирования структуры, принудительной загрузки чанков, запросов соседних capabilities, повторного входа в FE-операции и уведомлений. Конкретный механизм отслеживает изменение структуры. `protected final void onEnergyPortAvailabilityChanged()` сообщает об изменении; приватный `synchronizeAvailableEnergyPorts()` делегирует `refreshAvailablePorts()` вне FE-транзакций. Тот же метод используется при onLoad и фактической смене режима. Согласование событийное, без обязательного пересчёта каждый тик; живая проверка на каждой операции сохраняется.
