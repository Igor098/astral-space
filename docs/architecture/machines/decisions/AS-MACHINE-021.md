# AS-MACHINE-021 — Независимые визуальные разъёмы и необязательная анимация механизмов

**Статус:** архитектурный принцип утверждён 2026-11-05; реализация ещё не выполнена.  
**Область:** клиентская отрисовка механизмов Astral Space (Minecraft 1.21.11 / NeoForge 1.21.11).  
**Связанные документы:** [Архитектура механизмов](../README.md), [Ресурсные подключения](../resource-connections.md).

## Решение

1. Энергетические и предметные разъёмы — **независимые визуальные элементы**, которые могут одновременно присутствовать на одной грани, если это разрешает конструкция механизма. Один универсальный взаимоисключающий разъём вместо них не используется.
2. Состав отображаемых разъёмов определяется серверной конфигурацией механизма. Визуализация — **клиентская проекция**, а не источник разрешений на передачу ресурсов.
3. Корпус, неподвижные панели и разъёмы отрисовываются как статическая геометрия. Для таких частей не требуется покадровая отрисовка всей машины лишь из-за наличия изменяемой конфигурации.
4. Отдельные механизмы **могут** иметь анимированные 3D-детали: шестерни, вентиляторы, поршни, створки, энергетические ядра и т. п. Анимация необязательна для машин без движущихся элементов и не должна заставлять пересобирать статическую модель каждый кадр.
5. Возможность *отображать* несколько типов разъёмов на одной грани **не означает**, что к ней автоматически можно подключить несколько физических кабелей/труб или обойти правила capability и маршрутизации.

## Область применения: одноблочные машины и мультиблоки

Независимые визуальные разъёмы на одной грани прежде всего предназначены для **одноблочных механизмов**, конструкция которых поддерживает несколько ресурсных каналов.

Для будущих **мультиблоков** выбран более простой целевой подход: отдельные специализированные физические блоки для входа/выхода энергии, предметов, жидкостей и других ресурсов. Мультиблочный хэтч не обязан совмещать разные ресурсные функции или показывать несколько типов разъёмов на одной поверхности. Наличие нескольких отдельных хэтчей не исключает общую работу через контроллер.

Это не меняет принципа отделения статической геометрии от необязательных анимаций: специализированные блоки-порты тоже могут использовать простой статический рендеринг.

## Текущее состояние Coal Generator Mk I

На коммите `3c1ddff` (2026-11-05) пять `BlockState.OUTPUT_*` используются для включения выходов; `coal_generator.json` описывает их через `multipart`. В энергетической части уже интегрированы `EnergyComponent`, `EnergyTransferCoordinator`, `EnergyTransferBudget`, `EnergyPortHandler` и `EnergyPushTransfer`. Динамическая композиция визуальных разъёмов и предметные внешние разъёмы **ещё не реализованы**.

## Намеченный путь внедрения (не утверждённый Java API)

1. Перенести источник истины режимов выходов из `BlockState` в `EnergyPortConfiguration` внутри `BlockEntity`.
2. Согласовать NBT-сохранение, серверную обработку переключений, GUI и синхронизацию визуального состояния клиента.
3. Проверить применимость актуальных для NeoForge 1.21.11 `BlockStateModel` и данных модели для композиции запечённых статических элементов.
4. Для действительно движущихся деталей использовать отдельную систему анимированного рендеринга; кандидат — `BlockEntityRenderer` с актуальным render-state API.
5. Только после переноса зависимостей убрать `BlockState.OUTPUT_*` и соответствующий старый `multipart`.

## Вопросы, остающиеся открытыми

- API визуального состояния, синхронизация и обновление геометрии чанка.
- Геометрия нескольких разъёмов на одной грани и конфликты с анимированными деталями.
- Физическое подключение нескольких транспортов, жидкостные/газовые разъёмы, мультиблоки.
- Правила анимаций, интерполяции и ограничения производительности.

**Граница решения:** утверждены архитектурные принципы, но не конкретные классы, схемы пакетов или законченная реализация.

## Результат локального визуального spike (2026-11-05)

**Уточнение статуса:** утверждённый принцип независимых разъёмов уже проверен в **локальном тестовом блоке**, но **не внедрён в Coal Generator Mk I и не подтверждён в `main`**. Старые формулировки выше о «не выполнено» относятся к производственной системе.

В `VisualTestBlock` / `VisualTestBlockEntity` пользователь добился переключения двух независимых визуальных областей (embedded: заглушка или энергетический модуль; overlay: предметный модуль поверх постоянной панели) без дополнительных `OUTPUT_*` в `BlockState`. Сервер синхронизирует целочисленную маску с клиентом; `ModelData`, `DynamicBlockStateModel.collectParts()`, `CustomUnbakedBlockStateModel`, запечённые `BlockModelPart` и ориентация через `ModelState` обеспечили видимое переключение и поворот по `FACING`. Для перестройки уже нарисованного чанка понадобилось дополнительное клиентское уведомление. Также исправлена щель экспериментального корпуса.

**Архитектурный вывод:** поддерживать именованные области, где сами машины задают геометрию, разрешённые варианты и оформление отсутствия порта; не переносить тестовую `visualMask` в качестве универсального API. Клиентская геометрия не является источником разрешений передачи. См. [прототип](../visual-model-prototype.md).

**Дополнение о физической стыковке:** независимые визуальные области не привязаны к числу проводов в одной клетке. Для собственных коммуникаций согласована составная многоканальная система с автоматической визуальной обёрткой (см. [AS-MACHINE-022](AS-MACHINE-022.md)); внешние моды пользуются стандартными capabilities по стороне. Окончательные модели разъёмов и геометрия переходов не утверждены.
