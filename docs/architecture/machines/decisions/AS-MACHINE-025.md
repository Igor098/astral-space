# AS-MACHINE-025 — GenerationProcess и транзакционный топливный цикл генераторов

**Статус:** утверждено как целевая архитектура 2026-11-24; новые компоненты/интерфейсы и рефакторинг Coal/Lava пока не реализованы.  
**Область:** производственный процесс генераторов на предметном и жидкостном топливе.  
**Связанные решения:** [023](AS-MACHINE-023.md), [024](AS-MACHINE-024.md); [сохранение](../persistence-and-networking.md); [тесты](../test-matrix.md).

## Проблема и выбранное решение

Дублирование топливных `burnTime`/`burnDuration` и логики списания Coal/Lava устраняется **минимальной композицией со Strategy**, а не промежуточным `AbstractFuelCycleGeneratorBlockEntity` и не прямыми топливными хуками в базовом генераторе.

- `AbstractGeneratorBlockEntity` владеет общим FE-алгоритмом, хранит ссылку на `GenerationProcess` и **не содержит** топливных счётчиков.
- `FuelCycleGenerationProcess` управляет общим топливным циклом Coal/Lava, **владеет** одним `FuelCycleComponent` и получает узкое действие списания топлива.
- Coal предоставляет предметный источник и его правила, Lava — жидкостный. Ни общий процесс, ни `FuelCycleComponent` не получают напрямую `EnergyComponent`, `Level`, `BlockEntity` и FE-порты.
- Нетопливные процессы могут реализовывать ту же Strategy без фиктивного топливного компонента. Различия уровней Mk I/II/III с одинаковым алгоритмом задаются конфигурацией.

## Утверждённые Java-контракты

```java
public interface GenerationProcess {
    boolean prepareProductionTick();
    void onProductionTickCompleted();
}

public interface PersistentGenerationProcess extends GenerationProcess {
    void saveState(ValueOutput output);
    void restoreState(ValueInput input);
}

@FunctionalInterface
public interface FuelConsumption {
    OptionalInt tryConsume(TransactionContext transaction);
}
```

- `prepareProductionTick()` вызывается **после** серверных проверок, достаточного места под *полную* порцию FE и редстоуна; разрешает продолжить оплаченный цикл либо пытается запустить новый. Сам не добавляет FE и не выполняет Push/Pull. `false` останавливает производственный тик.
- `onProductionTickCompleted()` вызывается **только после успешной полной записи FE**. Для топлива уменьшает остаток цикла на один тик. Метод не списывает следующую порцию топлива, не выполняет Push/Pull и не управляет FE-бюджетами. Новый цикл запускается только при следующей допустимой подготовке производственного тика.
- `PersistentGenerationProcess` **необязателен**: процесс без сохраняемого состояния не реализует его. Базовый генератор при наличии этого контракта делегирует сохранение/восстановление в `generation_process`.
- `FuelConsumption.tryConsume(tx)` работает в предоставленном контексте и возвращает **строго положительную** длительность только при полном успешном извлечении требуемого топлива; `OptionalInt.empty()` означает неуспех. Источник **не открывает и не коммитит собственную корневую транзакцию**. Не вводить иерархию `FuelSource`/адаптеры без доказанной необходимости; смысловой интерфейс предпочтительнее сырого `Function`.

Двухметодного `GenerationProcess` достаточно: не вводить обязательные `GenerationContext`, универсальный менеджер процессов или фабрики процессов без доказанной необходимости. Конкретный Coal/Lava может передать `FuelConsumption` ссылкой на собственный метод (например, `this::tryConsumeFuel`, имя иллюстративное) либо лямбдой с уже созданным хранилищем. Отдельные обязательные классы `CoalFuelSource`, `LavaFuelSource` и фабрики не требуются.

## FuelCycleComponent

Согласован минимальный публичный контракт **final-класса** (эскиз сигнатур, без тел методов):

```java
public final class FuelCycleComponent {
    public FuelCycleComponent(Runnable onCycleChanged);

    public boolean isActive();
    public int getRemainingTicks();
    public int getTotalTicks();
    public void start(int durationTicks, TransactionContext transaction);
    public void completeProductionTick();

    public void serialize(ValueOutput output);
    public void deserialize(ValueInput input);
}
```

Наследование от компонента не предусмотрено; расширение алгоритма выполняется через `GenerationProcess` и композицию.

- Конструктор проверяет переданный `Runnable` через `Objects.requireNonNull()` (при null — `NullPointerException`) и сохраняет ссылку на него. Устанавливает `remainingTicks=0` и `totalTicks=0`, **не вызывает callback**. Не принимает `Level`, `BlockEntity`, `TransactionContext`, `EnergyComponent`, хранилище, конкретный вид топлива, начальную или максимальную длительность.
- `isActive()` истинно ровно при `remainingTicks>0`.
- `start(duration, tx)`: `duration>0` (иначе **`IllegalArgumentException`**), ненулевой `TransactionContext` (**`NullPointerException`**), запуск **поверх активного** цикла запрещён (**`IllegalStateException`**). Метод возвращает **`void`**, не превращает ошибки программного контракта в `false`. Неактивное завершённое `0 / total` допускает новый запуск. При старте **оба значения становятся равны `durationTicks`**; компонент регистрирует **совместный снимок обоих int** через `SnapshotJournal` до изменения.
- `completeProductionTick()` — нетранзакционный декремент `remainingTicks` **ровно на 1**, только при активном цикле; вызов при нуле — **`IllegalStateException`** и отсутствие изменений. `totalTicks` при завершении остаётся положительным для GUI; метод не открывает транзакцию. Обычные чтения `isActive/getRemainingTicks/getTotalTicks` **не вызывают callbacks**.
- При старте callback вызывается **только после корневого commit и фактического изменения**, при завершении тика — сразу после изменения; при конструировании, rollback и NBT-восстановлении callbacks отсутствуют. Компонент сам не вызывает `setChanged()`. Необходимые последствия изменения состояния выполняет callback владельца; пример передачи — `this::onFuelCycleChanged` (имя иллюстративное). Передавать callback при сборке безопасно, поскольку он не вызывается при конструировании или тихом восстановлении. Точный состав действий обработчика владельца ещё не утверждён.

## Одна транзакция на запуск цикла

`FuelCycleGenerationProcess` открывает **одну корневую NeoForge `Transaction`** для расхода конкретного Item/Fluid-топлива и `FuelCycleComponent.start(..., tx)`; подтверждает её только при полном успехе. При неуспехе или исключении до `commit` обе части должны откатиться. Счётчики нельзя присвоить обычным нетранзакционным способом между извлечением топлива и commit.

После открытия/подтверждения нового цикла сохраняется прежняя гарантия `FULL-TICK-OR-PAUSE`: расход одного производственного тика — **после** фактической полной записи FE. Однако сама запись произведённой FE через `EnergyComponent.storeProducedEnergy` **нетранзакционная**; атомарность всего тика (включая FE) настоящим решением **не обещается**. Исключительные сбои полной записи должны быть отдельно обработаны и протестированы.

## Создание и привязка процесса

`AbstractGeneratorBlockEntity` не может конструировать процесс, которому нужны ещё не созданные хранилища потомка. Поэтому:

1. Родитель создаёт общую FE-инфраструктуру.
2. Конкретный Coal/Lava создаёт свои топливные хранилища.
3. Конкретный генератор создаёт `FuelCycleComponent` и `FuelCycleGenerationProcess`.
4. Через **защищённый final-метод однократно привязывает** готовый `GenerationProcess` к базовому генератору.

К завершению конструктора конкретной BlockEntity процесс обязан быть привязан; откладывать привязку до `onLoad()` нельзя. Повторная привязка и горячая замена запрещены; перед любым использованием проверяется наличие процесса. Его отсутствие — ошибка инициализации, а не штатный результат false. Привязка сама не запускает генерацию, восстановление NBT или клиентскую синхронизацию. Ссылка базового генератора может быть не `final` — принятый компромисс. Из родительского конструктора не вызывать переопределяемые методы, не обращаться к ещё не заданному `Level`, не вызывать callback компонентов. Точное имя метода привязки не утверждено.

## NBT и восстановление

Структура **нового единственного** формата (без миграции старых `burnTime`/`burnDuration`):

```text
generation_process
└── fuel_cycle
    ├── remaining_ticks: int
    └── total_ticks: int
```

- `AbstractGeneratorBlockEntity` создаёт `generation_process` и через `PersistentGenerationProcess.saveState/restoreState` делегирует управление. `FuelCycleGenerationProcess` создаёт `fuel_cycle`, затем вызывает `FuelCycleComponent.serialize/deserialize` с **готовой секцией**.
- Инвариант `0 <= remaining_ticks <= total_ticks`. Корректны пустое `0/0`, активное `remaining>0` и законченное `0/total`, где `total>0`.
- При отсутствии **всей** секции состояние `0/0`. При отсутствии хотя бы одного поля, неверном NBT-типе либо нарушении инварианта **весь цикл сбрасывается в `0/0`**; не исправлять повреждённое значение частичным clamp.
- `deserialize` читает каждое поле через `ValueInput.getInt(key)` (результат `Optional<Integer>`), **не** `getIntOr(key, 0)`: отсутствующий ключ нельзя ошибочно признать корректным нулём. При реализации необходимо тестами подтвердить фактическую семантику `ValueInput.getInt()` на неверно типизированных данных в целевой версии Minecraft; выбор метода не является подтверждением, что он различает все требуемые случаи. Утверждённое правило сброса всей пары при неверном типе сохраняется.
- `loadAdditional` восстанавливает **тихо**, без `Transaction`, `SnapshotJournal`, callback, `setChanged()`, сети и мира. До `loadAdditional` все компоненты созданы и процесс привязан. `onLoad` затем выполняет идемпотентную серверную синхронизацию.

## Инварианты интеграции и сохранения последней длительности

- **Пауза сохраняет оплаченный цикл**, а не возвращает когда-то списанную единицу угля/порцию лавы во входное хранилище. После снятия редстоуна или освобождения FE-буфера тот же `remainingTicks` продолжается **без повторного расхода топлива**. Во время паузы уже накопленная FE может передаваться наружу через разрешённые порты, а отображаемая текущая выработка равна `0`.
- В `fuel_cycle` сохраняются **только два обязательных int-поля** `remaining_ticks` и `total_ticks`. Не создавать вторую копию `isBurning`, `isActive`, `fuelType` или старых `burnTime/burnDuration` на уровне базового генератора. `isActive` вычисляется через `remainingTicks > 0`.
- **Универсальный компонент не вводит глобальный верхний предел времени топлива** сверх диапазона корректного `int`; отдельное ограничение конкретного топлива возможно только по обоснованному механическому требованию. Восстановление сохраняет завершённое `0/total` для GUI.
- При `serialize/deserialize` входной `ValueOutput/ValueInput` не может быть `null`; отсутствие вложенного раздела обрабатывается через `childOrEmpty`, а **не** через передачу `null` компоненту.
- Правила возврата оставшегося топлива **при разрушении самой машины** этим ADR не определены. Не приписывать обычной паузе или выгрузке логику возврата физических предметов/жидкости.

## Точное делегирование сохранения и контракт источника

`FuelCycleGenerationProcess` реализует `PersistentGenerationProcess` и делегирует:

```java
@Override
public void saveState(ValueOutput output) {
    fuelCycle.serialize(output.child("fuel_cycle"));
}

@Override
public void restoreState(ValueInput input) {
    fuelCycle.deserialize(input.childOrEmpty("fuel_cycle"));
}
```

Базовый генератор создаёт и передаёт секцию `generation_process` только для процесса, реализующего `PersistentGenerationProcess`. `serialize()` не меняет состояние и не вызывает callback. Восстановление выполняется до штатной работы, при отсутствии незавершённой транзакции над состоянием цикла.

`FuelConsumption` определяет пригодность ресурса, количество порции и длительность, но не управляет `FuelCycleComponent`, не записывает произведённую FE и не выполняет Push/Pull. `OptionalInt.of(durationTicks)` означает полное извлечение внутри ещё открытой транзакции, а не окончательное подтверждение расхода. Если источник извлёк только часть требуемой порции, но вернул положительную длительность, это нарушение контракта источника: общий процесс не знает количества конкретного топлива и не обязан самостоятельно обнаруживать такой ошибочный результат. Полнота извлечения проверяется тестами конкретного Item/Fluid-источника. При активном цикле источник повторно не вызывается. При empty (включая частичное извлечение) либо недопустимой длительности корневая транзакция не подтверждается; изменения откатываются. Предметный и жидкостный источники также не должны вызывать `setChanged()` в связи с ещё неподтверждённым списанием, публиковать успешное изменение, клиентские уведомления или инвалидации, основанные на неподтверждённом состоянии, до root commit. Конкретное согласование callbacks с `onRootCommit()` остаётся задачей реализации, а не новым утверждённым Java API.

## Не путать целевую модель с реализованной

В текущем `main` Lava извлекает жидкость в транзакции, но обычным присваиванием задаёт `burnTime/burnDuration`; Coal подтверждает транзакцию списания предмета отдельно от изменения времени цикла. Эти схемы **должны быть заменены при реализации**, но сам документационный ADR код не меняет.

Сигнатуры и правила выше **согласованы**; Java-пакеты, конкретный вид снимка `SnapshotJournal`, сообщения исключений и unit/integration тесты — детали реализации.
