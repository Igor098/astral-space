# AS-MACHINE-027 — FE-потребители и энергетические накопители

**Статус:** утверждены архитектурные роли, общий FE-буфер и целевая иерархия с `AbstractEnergyConsumerBlockEntity`; конкретные конструкторы/Java API пока не утверждены. Целевая иерархия уточнена аудитом 9.17.A ниже.  
**Актуализировано:** 2026-11-24.  
**Область:** компрессоры, дробилки, электропечи, аккумуляторы и другие механизмы с внешним FE-вводом и/или выводом.  
**Связанные решения:** [AS-MACHINE-023](AS-MACHINE-023.md) — общий FE-буфер, контроллеры и портовый диспетчер; [AS-MACHINE-024](AS-MACHINE-024.md) — правила FE-портов; [AS-MACHINE-011](AS-MACHINE-011.md) — полностью оплаченный рабочий такт; [энергетическая подсистема](../energy-system.md).

## Роли FE-механизмов

Согласованный принцип — **один внутренний `EnergyComponent` на экземпляр энергетической BlockEntity**, отдельно подключаемые направления передачи. Ни наличие буфера, ни наследование от энергетического базового класса сами по себе **не открывают** внешнюю FE capability.

| Тип механизма | Внешний FE-ввод | Внешний FE-вывод | Собственная генерация | Активный Push | Расход FE на работу |
|---|---|---|---|---|---|
| Coal/Lava Generator | Нет | Да | Да | Да | Не входит в общую модель генератора |
| Consumer: компрессор, дробилка, электропечь | Да | Нет | Нет | Нет | Да |
| Energy Storage: аккумулятор/накопитель | Да | Да | Нет | Да | Нет по умолчанию |

Это **контракты типовых ролей** с определённым целевым местом потребителя и накопителя в иерархии; реализация этих классов ещё впереди. Гибридные машины, одновременно производящие FE и расходующие её для другого процесса, **не входят в текущие подтверждённые игровые требования**: не добавлять ради них обязательные направления и классы всем механизмам заранее.

## Общая FE-база

`AbstractEnergyMachineBlockEntity` (целевая, ещё не реализованная база) владеет единственным `EnergyComponent`: хранение FE в `long`, чтение количества/вместимости, реакция на изменения, тихое восстановление сохранения. Он **не обязан** иметь `EnergyInputController`, `EnergyOutputController`, `EnergyPortConfiguration`, `EnergyDistributionManager`, `EnergyPushTransfer`, бюджеты, редстоун, рецепты или визуальную модель.

Содержание буфера не следует копировать в портовые обработчики, входной/выходной контроллер, рецептурную камеру или хэтч. `EnergyComponent` предоставляет, в зависимости от назначений, существующие `insertEnergy(..., TransactionContext)`, `extractEnergy(..., TransactionContext)`, `tryConsumeForWork(..., TransactionContext)` и `restoreStoredEnergy(long)`. Это разные операции: **внутренняя трата FE на работу не равна внешнему извлечению через OUTPUT-порт**.

**Машинная роль определяет доступные внешние операции, а не наличие FE-буфера.** Портовые обработчики и конфигурации подключаются там, где механизм их действительно поддерживает.

## Consumer — потребитель энергии

### Принятое поведение

Примеры: `ElectricCompressorBlockEntity`, `ElectricCrusherBlockEntity`, `ElectricFurnaceBlockEntity`. Их типовая роль — **принимать FE извне и расходовать накопленную энергию для работы**, но **не отдавать FE** наружу.

- Снаружи допустимы `EnergyPortMode.INPUT` и `DISABLED`. `OUTPUT` не должен появляться из недопустимого GUI-запроса, конфигурации или сохранённых данных. Живая `EnergyPortPolicy` проверяется **при каждой** операции, включая ранее полученный `EnergyPortHandler`.
- Входящий `EnergyInputController` (рабочее имя, точный Java API ещё открыт) обрабатывает только **внешний `insert`**, учитывает **общий входной `EnergyTransferBudget` за игровой тик** по всем разрешённым входам и транзакционно записывает FE в общий `EnergyComponent`.
- Для input-only Consumer **не создаются фиктивные** `EnergyOutputController`, `EnergyDistributionManager`, `EnergyTransferTracker`, исходящий бюджет или `EnergyPushTransfer`. `extract` через общий портовый dispatcher возвращает `0`; политика также блокирует OUTPUT.
- Внутреннее **производственное потребление FE** инициируется логикой конкретной машины, **не** входным контроллером. Рецепт, прогресс, условия запуска, обработка предметов/жидкостей, редстоун и состояния меню **не** входят в FE-базу и `EnergyInputController`.
- При необходимости владелец использует независимый `RedstoneControlComponent` по [AS-MACHINE-028](AS-MACHINE-028.md). Компонент не является обязательным для FE-потребителя или накопителя; конкретные ограничиваемые операции определяет сам механизм. Управление выдачей накопителя редстоуном пока не утверждено.
- Согласно правилу полностью оплаченного рабочего тика, операция потребляет требуемые `N FE` целиком либо приостанавливается **без частичного списания тактовой цены и прогресса**. `EnergyComponent.tryConsumeForWork` уже имеет транзакционную семантику, но **конкретный** алгоритм процессора/камеры ещё предстоит спроектировать.
- При остановке производства накопленная FE не исчезает; само наличие энергии не обязывает машину выполнять работу. Пауза по FE отличается от доступности входного capability.

### Утверждённая роль иерархии (конструкторы ещё не утверждены)

```text
AbstractEnergyMachineBlockEntity
└── AbstractEnergyConsumerBlockEntity
    ├── ElectricCompressorBlockEntity
    ├── ElectricCrusherBlockEntity
    └── ElectricFurnaceBlockEntity

AbstractEnergyMachineBlockEntity владеет единственным EnergyComponent.
AbstractEnergyConsumerBlockEntity собирает INPUT-контур:
  EnergyPortPolicy + EnergyPortHandler
  EnergyPortDispatcher → EnergyInputController → EnergyComponent
Конкретная Consumer BE выполняет внутренние рабочие операции
через EnergyComponent.tryConsumeForWork(...) без внешнего OUTPUT.
```

**`AbstractEnergyConsumerBlockEntity` включён в утверждённую целевую иерархию.** Он переиспользует ввод FE и его политику для потребителей, не перенося в базу рецепты и процессинг. Требуется спроектировать точные конструкторы, NBT-делегирование портов и безопасную сборку входного контроллера без обращения к миру в конструкторе; отсутствие утверждённых сигнатур **не отменяет решения о базовом классе**.

## Energy Storage — накопитель FE

Накопитель **не производит энергию** и обычно **не расходует её как цену производственной операции**. Он принимает, хранит и выдаёт FE; это три разных ответственности:

- **Хранение:** тот же единственный `EnergyComponent` из FE-базы.
- **Внешний INPUT:** собственный `EnergyInputController` и **общий INPUT-бюджет** за тик.
- **Внешний OUTPUT:** собственный `EnergyOutputController`, `EnergyDistributionManager`, `EnergyTransferTracker` и **общий OUTPUT-бюджет** за тик. Внешний Pull разрешён OUTPUT-политикой; накопитель сам инициирует Push к соседям через разрешённые OUTPUT-порты, как генератор ([AS-MACHINE-003](AS-MACHINE-003.md)), и использует переиспользуемый `EnergyPushTransfer`, а не наследование от генератора.

```text
Наследование:
AbstractEnergyMachineBlockEntity
└── EnergyStorageBlockEntity

Владение компонентами:
AbstractEnergyMachineBlockEntity:
  EnergyComponent (единственный FE-буфер)
EnergyStorageBlockEntity:
  EnergyInputController  ── INPUT budget
  EnergyOutputController ── OUTPUT budget + distribution + tracker
  EnergyPortDispatcher  ── getStoredEnergy/getCapacity/insert/extract
  EnergyPushTransfer ── активная отправка соседям через OUTPUT-контур

Оба контроллера работают с унаследованным EnergyComponent.
```

**Бюджеты входа и выхода — независимые экземпляры и независимые лимиты.** Они **не объединяются** в один двунаправленный бюджет и **не дублируют** энергетический запас. Активный Push накопителя и внешний Pull расходуют **один общий OUTPUT-бюджет**, точно так же, как у генератора; Push не регистрируется как Pull-спрос.

Пример для понимания независимости лимитов: при `inputLimit=100 FE/t` и `outputLimit=80 FE/t` возможна внешняя вставка до 100 FE и внешняя выдача до 80 FE **в том же тике**, если запас, портовые правила и транзакции это позволяют. Эти числа **иллюстративны, не утверждённые игровые характеристики конкретного аккумулятора**. В реальном поведении все вставки/извлечения проверяют свободное место/остаток общего `EnergyComponent`, доступность порта, соответствующий бюджет и транзакционный результат.

**Не наследовать накопитель от `AbstractGeneratorBlockEntity` ради готового Push**: нет собственной генерации и топливного процесса. Отдельный `AbstractEnergyStorageBlockEntity` **пока не вводится** — он оправдан лишь при появлении общего накопительского lifecycle (режимов приоритета, автоотдачи, баланса и т. п.) у нескольких реальных машин. Это сознательно отложенный выбор, а не утверждённое требование создавать такой класс.

## Один EnergyPortHandler и EnergyPortDispatcher для разных ролей

Согласовано сохранять уже существующие `EnergyPortHandler` и `EnergyPortOperations`. Тонкий `EnergyPortDispatcher` (целевое рабочее имя) реализует ровно четыре метода интерфейса:

```text
getStoredEnergy()  ──► EnergyComponent.getStoredEnergy()
getCapacity()      ──► EnergyComponent.getCapacity()
insert(id,...,tx)  ──► EnergyInputController     (если подключён)
extract(id,...,tx) ──► EnergyOutputController    (если подключён; внешний PULL)
```

Если соответствующий контур отсутствует, операция `insert`/`extract` возвращает `0`. Это **не** разрешает обходить `EnergyPortPolicy`: она проверяется в `EnergyPortHandler` при каждом внешнем вызове, а контроллеры не должны позволять обход соответствующих направлений при прямых вызовах. Начальное получение capability и повторное использование выданного обработчика должны одинаково соблюдать текущую доступность порта.

Внешний `EnergyPortHandler.insert()` сохраняет возможность частичного приёма FE в пределах свободного места, разрешений и входного бюджета. `FULL-TICK-OR-PAUSE` относится к генерации, а не к внешней вставке: при свободных 30 FE запрос на 40 FE может принять 30 FE, если политика и бюджет разрешают.

**Портовый режим и бюджет — отдельные ограничения.** Например, INPUT-порт накопителя может быть разрешён, но вставка вернёт `0`, если общий FE-буфер заполнен или израсходован входной лимит. OUTPUT может быть доступен, но FE не выдаётся, если запас пуст или исчерпан исходящий лимит.

## Транзакции, сохранение и инварианты

- NeoForge `TransactionContext` участвует в FE-вставках, извлечениях и внутреннем расходовании FE. Неуспешная/отменённая транзакция не должна изменять окончательный запас или считать передачу состоявшейся и оплаченной. Проверка гипотетической доступности не равна подтверждённой передаче.
- Вложенная FE-секция общего энергетического базового класса — **единственное** сохраняемое место запаса; не сохранять второй независимый счётчик FE в Consumer/Storage/handler. Окончательное имя FE-секции в NBT остаётся открытым. Восстанавливать `EnergyComponent` тихо, без событий, а runtime-порты согласовывать после загрузки.
- Выбранные настройки портов сохраняются при наличии настраиваемого режима. Источником истины остаются `EnergyPortConfiguration` и живая `EnergyPortPolicy`, а не визуальные разъёмы или `BlockState`.
- Ни Input/Output-контроллер, ни накопитель не должны иметь скрытых дубликатов `EnergyComponent`, своих независимых запасов либо обходного пути передачи, который не использует соответствующие бюджеты.

## Что уже согласовано и что ещё открыто

**Закрыт архитектурный выбор:** общий FE-буфер; Consumer=input-only с расходом FE на внутреннюю работу; Energy Storage=input+output с активным Push без собственной генерации; независимые Input/Output-контуры; отдельные бюджеты INPUT/OUTPUT; один общий OUTPUT-бюджет Push/Pull; отсутствие фиктивного распределителя у Consumer; сохранение `EnergyPortHandler` и тонкий диспетчер.

**Место `AbstractEnergyConsumerBlockEntity` в иерархии утверждено**, но **не фиксировались точные Java-сигнатуры** его конструктора, `EnergyInputController`, возможного `AbstractEnergyStorageBlockEntity`, возможной фабрики Input, схемы NPC/GUI для аккумулятора, конкретные игровые FE/t значения, рецепты и общая система процессинга. Эти вопросы нельзя оформлять как уже готовый production-контракт.

Уточнение 2026-11-26: контракт общей `EnergyOutputFactory` согласован в [AS-MACHINE-023](AS-MACHINE-023.md). Накопитель переиспользует её для OUTPUT-контура; INPUT-контур и общий диспетчер собираются отдельно, над тем же `EnergyComponent`. Input-only потребитель не создаёт выходную фабрику или её компоненты. Это не утверждает новый уровень наследования или готовность интеграции накопителя.

**Реализация:** в `main` уже существуют общие FE-компоненты и действующие Coal Generator Mk I и Lava Generator Mk I; описанное разделение контроллеров, Consumer/Storage и их integration tests — целевая архитектура и план внедрения, а не утверждение готовых классов.

## Уточнение целевой иерархии (9.17.A, 2026-11-27)

По итогам аудита принято направление с функциональными базами Generator, Consumer и Storage и специализированным мультиблочным наследником каждой базы. Это уточняет прежнее решение выше о прямом наследовании конкретного накопителя без собственной абстрактной базы: в целевой схеме предусматривается AbstractStorageBlockEntity. Для Consumer рабочее название AbstractConsumerBlockEntity заменяет прежнее проектное AbstractEnergyConsumerBlockEntity. Имена и точные Java API будущих классов окончательно определяются при их реализации; заранее пустые классы не создавать. Мультиблочная инфраструктура переиспользуется через композицию, не через множественное наследование. Контракты INPUT/OUTPUT, единственный FE-буфер, независимые бюджеты и обязательный Push накопителя не меняются. См. [концептуальную архитектуру](../machine-architecture.md) и [026](AS-MACHINE-026.md).
