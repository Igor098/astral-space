## Отдельная вертикаль — FE-потребители и накопители (после общей FE-базы)

- [x] Согласованы **роли и границы** Consumer (INPUT + внутренний расход FE без внешнего OUTPUT) и Energy Storage (INPUT + OUTPUT с обязательным активным Push без собственной генерации) — [AS-MACHINE-027](decisions/AS-MACHINE-027.md).
- [ ] Реализовать `EnergyInputController` с единым INPUT-бюджетом, транзакционной вставкой FE и соблюдением живой политики портов; **не** навязывать входящему контуру выходной `EnergyDistributionManager` и `EnergyPushTransfer`.
- [ ] Реализовать утверждённый специализированный `AbstractEnergyConsumerBlockEntity` с INPUT-контуром над одним `EnergyComponent`, затем первую конкретную Consumer BlockEntity; внутреннюю производственную операцию спроектировать отдельно, с полным расходом FE за тик либо паузой без прогресса.
- [ ] Ввести первую конкретную Energy Storage BlockEntity с обоими контроллерами над одним буфером и **независимыми** INPUT/OUTPUT бюджетами; проверить параллельную вставку и выдачу в пределах соответствующих лимитов.
- [ ] Для обязательного активного Push накопителя использовать общий `EnergyPushTransfer` и тот же OUTPUT-бюджет Pull/Push; **не** наследовать накопитель от генератора ради Push.
- [x] Целевая иерархия потребителей определена: `AbstractEnergyConsumerBlockEntity` — прямой наследник общей FE-базы. Накопитель пока наследует `AbstractEnergyMachineBlockEntity` напрямую, без `AbstractEnergyStorageBlockEntity`.
- [ ] Утвердить точные конструкторы Consumer-базы и входного контроллера перед кодированием. Отдельный `AbstractEnergyStorageBlockEntity` рассматривать только при появлении уникальной общей логики накопителей.
- [ ] Добавить проверки rollback, `DISABLED`, устаревших внешних handlers, отсутствующего направления и NBT/GUI, не заявляя ещё не реализованный Consumer/Storage готовым.

## Этап 4. Производственные операции

- Определить контракт выбранного рецепта и запущенной операции.
- Реализовать атомарный запуск, паузу, сохранение прогресса, `WAITING_FOR_OUTPUT` и неделимую выдачу; до реализации согласовать механизм завершения, исключающий повторную выдачу при ошибке между размещением продукции и закрытием операции.
- Защитить сценарии смены рецепта при работающей операции.
- Многокомпонентные динамические слоты — следующим вертикальным срезом.

## Этап 5. Многокамерность

- Общие, индивидуальные и смешанные входы/выходы.
- Round Robin рабочих камер и правило полностью оплаченного такта FE.
- Резервирование только там, где в нём действительно есть необходимость.

## Этап 6. Жидкости, затем газы

- Роли `INPUT`/`OUTPUT`/`BIDIRECTIONAL`, фиксированные/динамические баки.
- Атомарность смешанных рецептов между типами ресурсов.
- Для газа отдельно определить идентификаторы, единицы, хранение, внешнее API и транспорт.

## Этап 7. Мультиблоки, SERVICE и возвраты

- Контроллер, физические хэтчи и их стабильные логические `portId`; уже согласованы `assemblyId`, `UNFORMED`/`FORMED`/`SUSPENDED`, fail-closed при неопределённой структуре и координация инвалидации по физическим хэтчам ([AS-MACHINE-026](decisions/AS-MACHINE-026.md)).
- Для мультиблоков спроектировать **специализированные блоки-порты** по ресурсу и роли (энергетический вход/выход, предметный вход/выход, жидкостные порты и др.), без требования совмещать ресурсы на одном хэтче.
- Учесть несколько отдельных хэтчей с одинаковым `Direction`, сохранив уникальные `EnergyPortId` и общие ресурсы контроллера.
- SERVICE-маршрут для извлечения входных ресурсов, независимо от обычного OUTPUT.
- Правила возврата несовместимых ресурсов и явного полного сброса с серверным разрешением.

## На каждом этапе

- Сначала контракт и тесты на инварианты, затем производственный код.
- Сохранять работу Coal Generator Mk I и регрессию Push/Pull/fairness.
- Не строить совместимость с несуществующими старыми мирами.
- Обновлять ADR при реальном изменении решения, а не при каждой внутренней оптимизации.
- Нагрузочное тестирование отложено по решению разработчика до более завершённого состояния мода.
