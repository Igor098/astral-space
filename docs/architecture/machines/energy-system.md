# Энергетическая подсистема (FE)

**Актуализировано:** 2026-11-24 (целевая архитектура); историческая интеграция Coal сверена по `3c1ddff` от 2026-11-05, актуальная интеграция Coal/Lava в `main` — по `3216128` после слияния PR #3. Локальные результаты тестов отмечены отдельно.  
**Связано:** [ADR-ENERGY-001/002 и статус миграции `EnergyPortId`](../energy/AstralSpace_Energy_Architecture_Decisions.md), [AS-MACHINE-003](decisions/AS-MACHINE-003.md), [AS-MACHINE-011](decisions/AS-MACHINE-011.md), [AS-MACHINE-023](decisions/AS-MACHINE-023.md), [AS-MACHINE-027](decisions/AS-MACHINE-027.md).

> Различать три состояния: **существует в Java**, **интегрировано в конкретный генератор**, **утверждено как целевая архитектура**. Это разные уровни готовности.

## Существующее состояние

| Компонент | Что уже реализовано | Ограничение текущего этапа |
|---|---|---|
| `EnergyComponent` | FE-хранилище `long`, `storeProducedEnergy`, транзакционные `insertEnergy`/`extractEnergy`/`tryConsumeForWork`, восстановление состояния | В Coal/Lava Generator Mk I используется для хранения FE; координация портов и лимитов вынесена в `EnergyTransferCoordinator` |
| `EnergyPortId` | Уникальный логический ID **в пределах механизма**, не мировой ID | Привязку к физической стороне обеспечивает машина/порт |
| `EnergyPortMode` | `INPUT`, `OUTPUT`, `DISABLED`; без `BOTH` | Подключение общей политики в каждый механизм — отдельная задача |
| `EnergyPortPolicy`, `FixedEnergyPortPolicy`, `ConfigurableEnergyPortPolicy` | Правила режимов, доступности, перенастройки | В обоих генераторах используется общий `EnergyPortHandler` |
| `EnergyPortConfiguration`, `EnergyPortConfigurationSerializer` | Конфигурация режимов и чтение/запись | Coal пока использует прежние флаги `BlockState` для выходов; Lava хранит конфигурацию в BE |
| `EnergyDistributionManager` | Спрос Pull, наблюдение Push, учёт выдачи, адаптивные квоты, `fairnessCredits` по `EnergyPortId` | Не перемещает FE и не применяет бюджет самостоятельно |
| `EnergyTransferBudget` | Транзакционный лимит передачи FE за тик | Push и Pull разделяют выходной бюджет (Coal 80 FE/t, Lava 120 FE/t); бюджет приёма существует отдельно |
| `EnergyTransferCoordinator` | Координация буфера, распределителя, бюджетов и статистики | Интегрирован в Coal/Lava Generator Mk I |
| `EnergyPushTransfer` | Активная отправка энергии соседям | Интегрирован в Coal/Lava Generator Mk I |
| `EnergyTransferTracker` | Учёт фактической выдачи для статистики | Это не источник авторизации передачи |
| `EnergyPortHandler` | **Реализован** как обработчик конкретного `EnergyPortId` | Coal/Lava кешируют экземпляры по `EnergyPortId`, проверки разрешений производятся при операции |

Ранее восемь компонентов базовой FE-модели имели **125 проходящих тестов** (исторический результат из архитектурной документации; не утверждение об актуальном полном прогоне). Отдельно после миграции и оптимизации распределителя локально прошли **66/66** тестов `EnergyDistributionManagerTest` и `EnergyLifecycleRegressionTest`.

**Синхронизация исходников:** базовая интеграция Coal (`3c1ddff`) и интеграция Lava (`3216128`, PR #3) присутствуют в `main`. ## Инварианты энергетических портов

- `INPUT` разрешает только приём FE, `OUTPUT` — только отдачу, `DISABLED` запрещает оба направления. `BOTH` не поддерживается.
- Порт идентифицируется `EnergyPortId`, а не `Direction` или `MachineSide`. Один `Direction` не обязан соответствовать единственному логическому порту в мультиблоке.
- Права проверяются при каждой операции: ранее полученный capability не даёт возможности обходить отключение порта.
- Режим `OUTPUT` — разрешение внешнего извлечения, **не** автоматическая Push-передача сама по себе.
- Push и Pull исходящего FE имеют **один общий бюджет**; нельзя списать энергию или бюджет дважды при конкурирующих операциях.
- Изменения состояния энергетической передачи и история менеджера корректно откатываются в NeoForge-транзакциях.

## `EnergyPortId`, `Direction` и `MachineSide`

`EnergyPortId` — стабильная идентичность участника распределения **внутри одной машины/контроллера**. В Coal Generator Mk I для пяти выходов используются собственные идентификаторы (например, `coal_generator.back`, `coal_generator.left`, `coal_generator.right`). Это **не** ID конкретного блока в мире.

`MachineSide` обозначает локальную сторону блока (`BACK`, `LEFT` и т. д.). `Direction` нужен для мирового соседства и контекста NeoForge block capability. Машина сопоставляет эти значения с `EnergyPortId`; `EnergyDistributionManager` ничего не знает о геометрии.

`updateAvailablePorts(List<EnergyPortId>)` определяет текущий набор и порядок участников. Порты, исключённые из набора, теряют накопленную историю; изменение порядка сохранённых участников само по себе её не сбрасывает. Наблюдения Push и обновление набора портов выполняются вне открытых транзакций.

Тест независимых логических портов с одинаковым физическим направлением **на реальном мультиблоке ещё нужен**: миграция менеджера не означает готовую систему хэтчей.

## Адаптивное распределение Push/Pull

- **Pull**: внешний сосед вызывает `extract()`, менеджер регистрирует Pull-запрос, а затем подтверждённое фактическое извлечение.
- **Push**: генератор опрашивает соседей и регистрирует **доступность**, отдельно выполняет транзакционную передачу и записывает её успешный объём.
- До первого обновления Push-наблюдений текущего тика учитывается доступность прошлого тика, чтобы избежать временной потери квот.
- `fairnessCredits` корректируют защиту долей по спросу и выдаче предыдущего тика; переносится строго история нужного тика, а не произвольные старые значения.
- Текущие и предыдущие запросы/извлечения, `fairnessCredits` изменяются транзакционно через `SnapshotJournal`.
- Актуальная **локально протестированная** реализация хранит снимки `UsageSnapshot`, `DemandSnapshot`, `FairnessSnapshot` компактными массивами пар `Object[]`; сами карты рабочего состояния остаются обычными коллекциями.
- Ни порядок обхода, ни ротация остаточных FE не должны теряться при последующих оптимизациях.

## Coal Generator Mk I — существующее поведение

- Буфер: **10 000 FE**.
- Генерация при работе: **40 FE/t**.
- Совокупный предел извлечения: **80 FE/t**, один для Push и Pull вместе.
- Доступные для настройки выходы: `BACK` (изначально включён), `LEFT`, `RIGHT`, `TOP`, `BOTTOM` (изначально выключены). `FRONT` не предоставляет FE-канал.
- На серверном тике Push выполняется **до генерации** и **после успешной генерации**. Оба прохода используют оставшийся общий лимит, чтобы только что произведённая энергия могла быть выдана в том же тике без превышения 80 FE/t.
- Сейчас флаги `BlockState.OUTPUT_*` используются для выбора выходов и изображения коннекторов. **Цель следующего этапа:** перенести источник истины в `EnergyPortConfiguration` BlockEntity, затем реализовать независимое динамическое отображение разъёмов без `BlockState.OUTPUT_*`; см. [AS-MACHINE-021](decisions/AS-MACHINE-021.md).
- Корректную рабочую логику топлива, редстоуна, обработки выдачи, лицевых состояний и текстур необходимо сохранить при интеграции, **кроме согласованного технического долга**: Coal мог записать частичную порцию FE при недостаточном свободном месте и расходовать топливный тик, тогда как Lava приостанавливался. Целевое правило FULL-TICK-OR-PAUSE устраняет это различие (см. [AS-MACHINE-023](decisions/AS-MACHINE-023.md)). Свободный зазор меньше полной порции не является потерей энергии и не требует компенсации.

## Историческое состояние интеграции и переход к целевой архитектуре

`EnergyComponent` отвечает за внутренний FE-буфер, а `EnergyTransferCoordinator` объединяет операции хранилища, распределителя, бюджетов и статистики. `EnergyPortHandler` интегрирован в Coal Generator Mk I. Это описание текущего реализованного контура. В целевой архитектуре алгоритмы `EnergyTransferCoordinator` переносятся в независимые контроллеры; координатор не остаётся обязательной обёрткой над ними, и мигрировавшая машина не использует обе реализации для одной FE-операции. Порядок миграции и удаление старого класса не утверждены. Перенос конфигурации из `BlockState` в `EnergyPortConfiguration` с NBT, серверными командами, GUI и клиентской визуальной проекцией остаётся задачей интеграции.

## Внутри многокамерной машины

Согласно [AS-MACHINE-011](decisions/AS-MACHINE-011.md), общий энергетический буфер обслуживает рабочие такты камер по Round Robin. Каждый шаг либо **полностью** оплачен, либо не выполняется; недостаток FE приостанавливает работу, а камера в `WAITING_FOR_OUTPUT` FE не тратит. Это отдельная будущая интеграция, а не функция текущего `EnergyDistributionManager` для внешних портов.

## Не завершено / не утверждено

- Интеграционные проверки Pull/Push, транзакций и уже полученных capabilities после изменения режимов.
- Перенос Coal Generator Mk I на `EnergyPortConfiguration` как источник режимов, NBT, GUI-проекцию и серверные команды; динамическая отрисовка независимых разъёмов.
- Физическая маршрутизация хэтчей мультиблока и тест одинакового `Direction` у независимых портов.
- Специальные машины, способные инициировать собственный активный FE-Pull.
- Общие правила энергетических апгрейдов и ограничения различных типов механизмов.
- Измерения TPS/MSPT при большом числе машин — отложены до более готовой версии мода.

## Целевая архитектура энергетических генераторов (решение 2026-11-24)

Полное обоснование: [AS-MACHINE-023](decisions/AS-MACHINE-023.md), [AS-MACHINE-024](decisions/AS-MACHINE-024.md), [AS-MACHINE-025](decisions/AS-MACHINE-025.md). **Это согласованные контракты, но не реализованные классы в `main`.**

### Тонкая FE-база и независимые контроллеры

- `AbstractEnergyMachineBlockEntity` владеет **единственным** `EnergyComponent`, связывает его с сохранением и lifecycle и не открывает FE capability только из-за наличия буфера. Нет обязательных портов, Push, бюджета, Fuel или Fluid.
- `AbstractGeneratorBlockEntity` владеет исходящим контуром и общей последовательностью производства. `EnergyInputController` обслуживает приём FE, `EnergyOutputController` — отдачу, распределение, статистику и **общий outgoing budget** для Push/Pull. Они могут работать с одним `EnergyComponent` без дублирования буфера.
- `EnergyPortDispatcher` — тонкий адаптер к существующему `EnergyPortOperations` для конечного `EnergyPortHandler`; не переписывает `EnergyDistributionManager`, `EnergyTransferBudget` или `EnergyPushTransfer`.

`EnergyOutputFactory.create(energy, ports, policy, maxOutputPerTick, currentTickSupplier)` собирает пять согласованных выходных компонентов: распределитель, бюджет, tracker, контроллер и Push. Генератор и накопитель переиспользуют эту сборку, сохраняя один буфер, общую политику и один OUTPUT-бюджет для Push/Pull. Фабрика не создаёт INPUT-контур, диспетчер или обработчики портов, не выполняет начальное согласование и не читает игровое время. Диспетчер подключает нужные направления отдельно. См. [AS-MACHINE-023](decisions/AS-MACHINE-023.md).

### Конфигурация и доступность

`GeneratorConfiguration` объединяет `GeneratorEnergySpec` (`long energyCapacity`, `int maxOutputPerTick`, `int generationPerTick`), правила `EnergyPortRules` и физическую `EnergyPortTopology`. Все три числовые характеристики строго положительны, а `generationPerTick <= energyCapacity`; номинальная генерация и исходящий лимит независимы. Отдельная спецификация производства не вводится, параметры топлива остаются специфическими для процесса/конкретного генератора. См. [AS-MACHINE-024](decisions/AS-MACHINE-024.md). Один механизм на первом этапе использует либо все FIXED-порты, либо все CONFIGURABLE; смешанные режимы отложены. У генераторов разрешены только `OUTPUT`/`DISABLED`. Наличие фиксированной позиции порта не означает фиксированного режима.

Общая `EnergyPortPolicyFactory.create(rules, availability, onConfigurationChanged)` собирает политику и, только для CONFIGURABLE, связанную с ней изменяемую конфигурацию. Для FIXED возвращает политику и `null` вместо конфигурации. Callback — обязательный `Consumer<EnergyPortId>` (не Runnable): получает изменённый ID один раз после записи режима, не вызывается при отказе, повторной установке, чтении, конструировании или тихом восстановлении. Фабрика не ограничена генераторами, создаёт независимые компоненты без обращения к миру и не вызывает переданные функции; см. [AS-MACHINE-024](decisions/AS-MACHINE-024.md).

`EnergyOutputController.refreshAvailablePorts()` — **утверждённый публичный метод без параметров**, который фильтрует неизменяемый упорядоченный список известных `EnergyPortId` через актуальную `EnergyPortPolicy` и передаёт результат в `EnergyDistributionManager.updateAvailablePorts(...)`. Вызов только **вне открытых FE-транзакций**, на безопасных границах. Текущий handler проверяет живую политику при **каждой** операции; прежняя ссылка не обходит отключение порта.

В целевой архитектуре `AbstractGeneratorBlockEntity` кэширует стабильный `EnergyPortHandler` на логический ID и предоставляет отдельный `EnergyEndpointHandler` на актуальную физическую привязку. Изменение только режима сохраняет привязку, а поворот/удаление/выгрузка отзывает устаревшие физические ссылки; инвалидация NeoForge не заменяет их защиту. Для генератора provider возвращает null при отсутствии стороны, доступного OUTPUT или готовности runtime; запас и бюджет не влияют на наличие capability. Регистрация через `RegisterCapabilitiesEvent` предназначена для конкретных BlockEntityType. Физические хэтчи требуют проверки владельца и инвалидации собственных позиций. См. [AS-MACHINE-023](decisions/AS-MACHINE-023.md), [AS-MACHINE-024](decisions/AS-MACHINE-024.md), [AS-MACHINE-026](decisions/AS-MACHINE-026.md).

### Активный Push (9.11)

Две фазы: Discovery с пробными вставками до номинального исходящего лимита в откатываемых корневых транзакциях и обновлением Push-доступности распределителя; затем Transfer с повторным поиском получателя и проверкой живой политики, отдельной транзакцией на порт и commit при положительной передаче. Обход — по ротируемому списку логических ID, физическая позиция и сторона определяются топологией; незагруженные чанки пропускаются. Discovery измеряет потенциальный приём даже при пустом FE-буфере. Два Push и внешний Pull делят общий бюджет одного тика. Подробный целевой алгоритм — [AS-MACHINE-023](decisions/AS-MACHINE-023.md). Интеграция ещё впереди.

### Производственный тик

Общий генератор реализует `FULL-TICK-OR-PAUSE`: возможный Push накопленной FE → проверка места под полную `generationPerTick` и разрешения редстоуна → `GenerationProcess.prepareProductionTick()` → запись **полной** порции FE → только при полном успехе `GenerationProcess.onProductionTickCompleted()` → возможный повторный Push в пределах того же бюджета.

Во время паузы по FE-буферу или редстоуну оставшийся топливный цикл не сокращается, новое топливо не списывается; внешняя выдача накопленной FE остаётся возможной. `FuelCycleGenerationProcess` и `FuelCycleComponent` — отдельные компоненты со строгим транзакционным стартом. Их API/NBT — в [AS-MACHINE-025](decisions/AS-MACHINE-025.md).

Редстоун-контроль генератора делегируется необязательному для общей архитектуры `RedstoneControlComponent` ([AS-MACHINE-028](decisions/AS-MACHINE-028.md)); проверка сигнала и ограничение именно производства остаются у владельца. Энергетический буфер, capability, Push/Pull и портовые правила не зависят от редстоуна.

### Последствия смены FE/Fluid-портов

`onLoad()` согласует доступные выходы после тихого NBT-восстановления; готовность серверного мира сама по себе недостаточна. При фактическом изменении FE-режима адресный callback передаёт ID: общий обработчик согласует распределение, помечает состояние для сохранения, при изменении предоставления capability инвалидирует позицию этого порта и вызывает необязательный hook с ID. Снимок всех режимов ради поиска изменившегося порта не требуется. Информация о старых физических привязках при повороте — отдельная задача. Изменения Fluid-портов Lava в целевой архитектуре не запускают FE-пересчёт; до миграции существующая Lava временно адаптирует Consumer к старому общему callback. `ModelData`/`DynamicBlockStateModel` остаются обязанностью конкретной машины.

### Открыто для реализации и регрессий

Нужно реализовать новые контроллеры и базовые классы без изменения FE-алгоритмов, проверить полный/неполный производственный тик, транзакции, callbacks, прежние capability после изменения порта, безопасную обработку исключительной неполной FE-записи и актуальный визуальный lifecycle. Не приписывать документационному PR реализацию этих возможностей.

## FE-потребители и энергохранилища (решение 2026-11-24)

**Канонический контракт:** [AS-MACHINE-027 — FE-потребители и энергетические накопители](decisions/AS-MACHINE-027.md). Общая архитектура портовых контроллеров описана в [AS-MACHINE-023](decisions/AS-MACHINE-023.md).

### Энергопотребитель (Consumer)

Электрические компрессоры, дробилки и печи **принимают FE** через INPUT-порты и **расходуют FE внутри механизма** на работу. Внешней выдачи у обычного потребителя нет: `OUTPUT` не входит в его допустимые режимы. `EnergyInputController` учитывает единый входной FE/t-бюджет и выполняет транзакционную вставку в **общий `EnergyComponent`**. Входному контуру **не нужны** `EnergyDistributionManager`, выходной бюджет, tracker или Push.

Внутренний рабочий такт выполняется только при достаточной энергии для всей стоимости `N FE`; недостаток энергии **приостанавливает производство** без частичного расходования стоимости и увеличения прогресса. Логика рецепта/камеры **не принадлежит** `EnergyInputController`. `EnergyComponent.tryConsumeForWork(..., TransactionContext)` уже существует; конкретные процессорные стратегии ещё не утверждены.

`AbstractEnergyConsumerBlockEntity` — **утверждённый специализированный уровень целевой иерархии** для компрессоров, дробилок и электрических печей. Он создаёт входную FE-инфраструктуру над единым `EnergyComponent`, не навязывая выходной распределитель, Push или конкретные рецепты. Java-конструкторы ещё не утверждены, и класс пока не реализован.

### Накопитель FE (Energy Storage)

Аккумулятор имеет **один реальный `EnergyComponent`**, через него работают **отдельные** `EnergyInputController` и `EnergyOutputController`. Их INPUT- и OUTPUT-бюджеты — **разные экземпляры**, поэтому внешний приём FE не расходует лимит выдачи, а внешняя выдача — лимит приёма. Активный Push накопителя через разрешённые OUTPUT-порты обязателен согласно AS-MACHINE-003 и AS-MACHINE-027; он использует тот же OUTPUT-контур и бюджет, что и Pull, без фиктивного Pull-спроса.

Накопитель **не производит FE**, самостоятельно инициирует Push через разрешённые OUTPUT-порты и не должен наследоваться от `AbstractGeneratorBlockEntity` только ради общего механизма отправки; `EnergyPushTransfer` проектируется переиспользуемым. Отдельный `AbstractEnergyStorageBlockEntity` допустим только после появления собственного общего lifecycle нескольких накопителей, а не вводится заранее. Конкретные правила конфигурации режимов и характеристики будущего аккумулятора пока не утверждены.

`EnergyPortDispatcher` остаётся общим четырёхметодным `EnergyPortOperations`-фасадом: читает количество/ёмкость из `EnergyComponent`, направляет insert во входной контур, extract (Pull) — в выходной; если направление физически не подключено, возвращает `0`. Установленная или ранее выданная capability **не обходит** живую `EnergyPortPolicy`.

**Статус реализации:** эти правила согласованы на уровне архитектуры, но новые Input/Output-контроллеры, Consumer/Storage BlockEntity и их полная интеграция в `main` ещё не готовы.

## Итог проектирования AbstractGeneratorBlockEntity (9.12.A.8–9.16, 2026-11-27)

- Общий серверный тик: первый Push, попытка полной порции через GenerationProcess, статистика и onProductionStateUpdated(producing), второй Push только после успеха при оставшемся общем бюджете. Неполная запись после подготовки — IllegalStateException без Completion, без обещания общего rollback.
- RedstoneControlComponent принадлежит генератору, ограничивает производство, не Push/Pull. Статистика производства и подтверждённой выдачи различается; визуальный hook не является командой перерисовки.
- Горизонтальная ориентация всего блока через protected final getFacing(), при отсутствии свойства NORTH. setBlockState обнаруживает поворот; отдельные уведомления изменения доступности и физической замены endpoint. Стабильный логический handler и отзываемая физическая обёртка имеют разный срок жизни.
- Формат energy/stored_energy, energy_ports, redstone_control_mode, generation_process утверждён; повреждённые CONFIGURABLE-порты отключаются, отсутствующие восстанавливаются по умолчанию. FIXED не сохраняет режимы. Редстоун fallback IGNORE.
- Полный API — [023](decisions/AS-MACHINE-023.md), физические привязки — [024](decisions/AS-MACHINE-024.md), NBT — [сохранение](persistence-and-networking.md), редстоун — [028](decisions/AS-MACHINE-028.md). Проектирование 9.1–9.16 завершено; 9.17–9.20 — реализация, ревью, тестирование, Javadoc и коммит. Не считать интеграцию Coal/Lava завершённой.

## Уточнение генераторного контура после 9.17.A (2026-11-27)

Независимые runtime-готовность, готовность конструкции и физическая доступность точки. isStructureReady() по умолчанию true, у будущего мультиблока отражает подтверждённую готовность сборки. Добавить проверку в isEnergyPortAvailable() и в начало tryProduceEnergy(). При неготовой структуре живая политика закрывает Push/Pull и capability, производственный процесс не подготавливается и не расходует топливо. Серверный тик продолжает штатный сброс статистики, первый Push с обновлением снимка доступности (включая пустой) и визуальный hook false; второй Push не выполняется. FE, настройки, остаток цикла и уже учтённые передачи сохраняются. Редстоун и статистика не смешиваются с проверкой структуры.

Логические и физические карты, общий бюджет, распределение, геометрический Push и final API сохраняются. Мультиблочный наследник отвечает за состояние сборки и проверку хэтчей, общая база — за энергетические последствия уведомлений. Не добавлять дополнительные hooks или реестр привязок заранее. См. [023](decisions/AS-MACHINE-023.md), [024](decisions/AS-MACHINE-024.md), [026](decisions/AS-MACHINE-026.md), [целевую иерархию](machine-architecture.md).

## Уточнение интеграции редстоуна (2026-11-27)

По [028](decisions/AS-MACHINE-028.md) генератор владеет RedstoneController, который инкапсулирует RedstoneControlComponent; реализует RedstoneControllable. Проверка производства теперь называется isRedstoneBlockingOperation(), смена режима — boolean changeRedstoneControlMode(mode). Энергетический контур, FE-политика, Push/Pull и общий бюджет остаются независимыми от редстоуна. Структурная готовность проверяется отдельно. Новые классы и интеграция ещё предстоят.
