# Грани, логические каналы, порты и маршрутизация

Основные ADR: [001](decisions/AS-MACHINE-001.md), [002](decisions/AS-MACHINE-002.md), [003](decisions/AS-MACHINE-003.md), [004](decisions/AS-MACHINE-004.md), [018](decisions/AS-MACHINE-018.md), [020](decisions/AS-MACHINE-020.md).

## 1. Иерархия концепций

```text
Блок / хэтч
  физическая грань (MachineSide → world Direction)
    ├── ENERGY    INPUT / OUTPUT / DISABLED
    ├── ITEM      INPUT route + OUTPUT route
    ├── FLUID     INPUT route + OUTPUT route + optional SERVICE route
    └── GAS       INPUT route + OUTPUT route + optional SERVICE route
```

Это **схема возможностей**, не утверждённые Java-enum для каждой строчки. Не каждая машина обязана иметь все каналы, а некоторые маршруты на конкретных гранях могут быть запрещены конструкцией.

## 2. Три слоя прав доступа

1. **Конструкция механизма:** канал/маршрут существует и разрешён ли он на данной грани.
2. **Настройка игрока:** разрешён ли доступ к маршруту на этой грани и разрешено ли активное действие (если поддерживается).
3. **Внутреннее хранилище и рецепт:** можно ли вставить/извлечь именно этот ресурс сейчас.

Все три слоя проверяются на сервере при каждой операции, в том числе через сохранённую третьим модом capability.

## 3. Пассивные и активные операции

| Канал | Пассивный вход | Пассивный выход | Активное действие машины |
|---|---|---|---|
| Энергия | `Energy INPUT` принимает FE | `Energy OUTPUT` отдаёт FE на Pull | Producer/storage Push из активного OUTPUT, **без отдельного GUI-флага** |
| Предметы | ITEM INPUT разрешает внешнюю вставку | ITEM OUTPUT разрешает извлечение результата | Необязательные АвтоВход / АвтоВыход на разрешённых маршрутах |
| Жидкости | FLUID INPUT | FLUID OUTPUT | Необязательные АвтоВход / АвтоВыход |
| Газы | GAS INPUT | GAS OUTPUT | Необязательные АвтоВход / АвтоВыход; собственный протокол газа пока открытый вопрос |
| Сервис | Не является обычным приёмом | `SERVICE` — ручное/внешнее извлечение из выбранного входного хранилища | **Нет** автоотправки через сервисный маршрут по умолчанию |

`DISABLED` для энергии — порт без разрешения передачи, `BOTH` **не существует**. Для предметов/жидкостей/газов **два независимых маршрута**, а не энергетический `BOTH`.

## 4. Сервисное извлечение — только SERVICE

Инварианты:
- Производственный OUTPUT никогда не предоставляет входное хранилище для внешнего извлечения.
- Входное хранилище можно освободить с помощью внешнего устройства, только если машина явно поддерживает сервисное подключение и оно разрешено.
- `SERVICE` по смыслу **маршрут извлечения**, а не новый вид ресурса/capability.
- Обычный маршрут `INPUT` не позволяет извлекать ингредиенты.
- Пока **не совмещаем** SERVICE и обычный OUTPUT *того же типа ресурса* на одной грани. Другие варианты совмещения ещё требуют дизайна.
- Частичная выкачка через сервисное подключение — обычная передача, не «частичный сброс» через GUI.

## 5. Несколько маршрутов → одно хранилище

Например, предметный `INPUT` сверху и слева ведёт в один слот электропечи. Предметный `OUTPUT` снизу и справа забирает содержимое одного выходного слота. Независимые гранные обработчики видят одну общую актуальную последовательность изменений, не копии предметов.

## 6. NeoForge 1.21.11

Внешняя совместимость для предметов, жидкости, энергии строится через `Capabilities.Item.BLOCK`, `Capabilities.Fluid.BLOCK`, `Capabilities.Energy.BLOCK`, с контекстом `Direction`. Множественные логические маршруты на одной грани необходимо отобразить в ту структуру обработчика, которую реально видит потребитель capability. Стандартного газового канала в списке встроенных возможностей NeoForge нет.

**Источник:** [официальная документация NeoForge 1.21.11 — Capabilities](https://docs.neoforged.net/docs/1.21.11/inventories/capabilities/).

Для меняющейся доступности capability учитываем актуальную проверку политик и инвалидацию кэша, если ранее возвращённый обработчик больше невалиден.

## 7. Специализированные порты мультиблоков — планируемая компоновка

Для будущих мультиблоков предполагаются **разные физические блоки-порты** для каждой нужной комбинации типа ресурса и назначения (например, вход и выход энергии; вход и выход предметов; вход и выход жидкости). Один физический хэтч не должен быть вынужден поддерживать несколько типов ресурсов или несколько противоположных ролей.

- Подключение внешней сети осуществляется через соответствующий специализированный блок.
- Внутренние буферы и правила работы принадлежат **контроллеру** мультиблока, а не копируются в каждом хэтче.
- Два хэтча одной машины, даже если они смотрят в один `Direction`, остаются разными физическими портами; для энергии — с разными `EnergyPortId`.
- Это не отменяет возможность **нескольких логических каналов на одной грани обычной одноблочной машины**, принятую в AS-MACHINE-001. Её визуализация отдельно рассматривается в AS-MACHINE-021.
- Конкретные блоки для `SERVICE`, правила физической стыковки и привязка к хранилищам **ещё не определены**.

**Статус:** планируемый дизайн, не реализованный API и не обязательство вносить изменения в существующий Coal Generator Mk I.

## 8. Не решено

- Как агрегировать несколько обслуживаемых входных баков через SERVICE без неоднозначности выбора.
- Совмещать ли `INPUT` и `SERVICE` одного вида на одной грани.
- Физическая ко-локация труб и кабелей на **одной грани одноблочного механизма**, а также интерфейс настроек каналов по видам ресурсов. Для мультиблоков планируются отдельные специализированные хэтчи.
